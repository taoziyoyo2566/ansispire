# 技术调查报告 (Technical Investigation Report) - VPS 并行批量部署方案

## 1. 调查概览 (Overview)
- **调查 ID**: `IVG-VPS-BATCH-PARALLEL`
- **关联任务**: VPS 管理插件并发性能优化
- **调查类型**: 架构探索 / 性能分析
- **目标**: 设计并验证一种基于 Ansible 原生并发能力（forks）的批量处理方案，以取代目前的串行处理模式。

## 2. 背景与问题描述 (Background)
- **初始观察**: `vps_manager` 插件目前在处理多个任务（如 `onboard`）时，采用 `for` 循环逐个启动 `ansible-playbook` 进程。
- **影响范围**: `plugins/vps_manager/` 插件核心逻辑。
- **触发条件**: 当 `runtime/inbox/vps/pending/` 目录下存在多个待处理任务时，处理时间随任务数量线性增长。

## 3. 调查过程 (Investigation Process)
### 3.1 假设 (Hypotheses)
1. **假设 A**: 使用 Python 多线程包裹 `ansible-playbook` 可以实现并发。 (结论：不推荐，违反 Ansible 最佳实践，日志输出混乱)。
2. **假设 B**: 将相同动作（Action）的任务聚合成一个多主机 Inventory，使用单个 Ansible 进程执行。 (结论：成立，性能最优且符合架构标准)。

### 3.2 方案设计 (Proposed Design)
- **任务聚合**: 按 `action` 字段对待处理任务进行切片分组。
- **动态 Inventory**: 将任务特有参数（端口、密钥等）注入为 `host_vars`。
- **结果回溯**: 通过动态注入自定义 Callback 插件 (`vps_batch_reporter`) 收集各节点的执行结果（成功/失败）。

## 4. 证据与日志 (Evidence & Logs)

all:

## 5. 发现与分析 (Findings)
- **核心原因**: 当前架构的瓶颈在于进程级的串行调度，没有利用 Ansible 擅长的 SSH 复用和并发连接。
- **技术细节**: 批量模式下需要解决“交互式密码输入”的预取问题。必须在 Ansible 启动前，通过 Python 批量提示用户输入所有节点缺失的凭据。
- **风险评估**: 并发写入 `vps_inventory.yml` 或 SSH 配置文件可能导致竞态冲突，必须在状态回写阶段引入进程内锁或顺序回写。

## 6. 结论与建议 (Conclusion)
- **行动方案**:
    1. 修改 `vps_manager.py` 的 `process_paths` 逻辑以支持分组。
    2. 实现 `build_ansible_inventory` 的批量模式。
    3. 编写临时的 Callback Reporter 插件用于状态采集。
- **修复方案**: 采用 Action Batching 架构。
- **经验教训**: 在开发 Ansible 封装工具时，应优先考虑 Ansible 的原生扩展能力（如 Inventory/Callback），而非在包裹层（Python/Go）重复实现并发控制。
