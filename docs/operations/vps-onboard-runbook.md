# VPS Onboarding Runbook (manual / break-glass)

End-to-end, field-verified command sequence for onboarding a fresh VPS using the
retained `playbooks/vps/` content, driven from a separate control node. This is
the **manual / break-glass path** — the Semaphore UI flow in
[`../feat-target-architecture/operator-guide.md`](../feat-target-architecture/operator-guide.md)
is the primary entry point. The playbooks here are committed project assets, while the
inventory + `vps_task` files are operator-local runtime input (kept under
`runtime/`, gitignored).

> **Convergence rule**: a host onboarded this way is initially known *only* to
> your local `runtime/onboard/*.ini` files — invisible to the Wizard, REST API,
> and audit templates. **After Phase 5, register it back into the Semaphore
> `vps-fleet` static inventory (Phase 6)** so all entry points share one truth.
> See the entry-point matrix in
> [feature-map `vps-lifecycle.md`](../reference/feature-map/vps-lifecycle.md).

---

## Topology & roles

| Host | Role | State |
|------|------|-------|
| **Control node** | runs `ansible-playbook` (agentless push) | stable box with toolchain (e.g. Debian 13) |
| **Target (VPS-A)** | the machine being onboarded | fresh VPS, reachable via a non-root user over SSH; must already have `python3` |

Do **not** onboard a host from itself — the SSH hardening would cut your own
session mid-run. Always drive from a separate control node.

### Placeholders used below

| Placeholder | Meaning | This run's value |
|-------------|---------|------------------|
| `<VPS_A_IP>` | target public IP | (your VPS-A IP) |
| `<BOOTSTRAP_USER>` | existing non-root user you can SSH in as | `deploy` |
| `<PROVIDER_KEY>` | existing provider/bootstrap key, used once to install the fleet public key | `~/.ssh/<provider key>` |
| fleet key | key used by both bootstrap transport and the managed user | `~/.ssh/ansispire_ansible` |
| managed user / port | account + SSH port onboard creates | `ansible` / `39222` |
| target OS | | Ubuntu 24.04 (Debian family → ufw applies) |

## Phase 0 — Control node setup

```bash
git clone -b feat/target-architecture <repo-url> ansispire
cd ansispire
make setup                  # venv + pip deps + galaxy collections; bakes ANSIBLE_* paths into .venv/bin/activate
source .venv/bin/activate   # afterwards run `ansible-playbook` directly — no manual exports needed
```

> **GOTCHA 1 — `make setup` fails at the end with "vault password file .vault_pass not found".**
> `ansible.cfg` sets `vault_password_file = .vault_pass` **globally**, so *every*
> ansible command needs that file to exist — even ones unrelated to vault. A
> fresh clone doesn't have it (it's gitignored). The first 3 setup steps
> (venv / deps / collections) already succeeded; only the final `make syntax`
> self-check failed. Fix by creating a vault password file:
> ```bash
> # The vault password is NOT generated by ansible — it's any passphrase you choose.
> # Regenerate a strong random one (high-entropy, mode 600, gitignored):
> openssl rand -base64 48 > .vault_pass && chmod 600 .vault_pass
> #   (no openssl: python3 -c "import secrets; print(secrets.token_urlsafe(48))" > .vault_pass && chmod 600 .vault_pass)
> ```
> Re-running `make setup` is **not** required after this — the toolchain is
> already installed; the error was only the self-check.

## Phase 1 — Verify toolchain

```bash
source .venv/bin/activate
ansible --version | head -1                                   # expect core >= 2.20.5
ansible-galaxy collection list 2>/dev/null | grep -iE 'ansible.posix|community.general'
ansible-playbook playbooks/vps/onboard.yml --syntax-check -i playbooks/vps/tests/syntax_inventory.yml
```

The third command should print `playbook: playbooks/vps/onboard.yml` with no error.

> **Note on ansible-core version drift**: `requirements.txt` pins
> `ansible-core>=2.20.5` (a lower bound, not `==`), so a fresh install pulls the
> latest matching release (e.g. 2.21.0). This is harmless for onboarding but is a
> real version-drift gap tracked under TASK-009 (dependency-security governance).

## Phase 2 — Prepare keys, inventory, and task files

```bash
# 2.1 — fleet keypair. Current onboard validation reuses the run's transport key,
#       so this SAME key must work for bootstrap and be installed for the managed user.
#       -N '' keeps this manual break-glass example non-interactive.
test -f ~/.ssh/ansispire_ansible || ssh-keygen -t ed25519 -N '' -f ~/.ssh/ansispire_ansible

# 2.2 — use the existing provider key once to trust the fleet key on bootstrap SSH.
ssh-copy-id -i ~/.ssh/ansispire_ansible.pub \
  -o IdentityFile=<PROVIDER_KEY> <BOOTSTRAP_USER>@<VPS_A_IP>

# 2.3 — runtime dir (gitignored)
mkdir -p runtime/onboard

# 2.4 — bootstrap inventory: connect with the fleet key just installed above.
cat > runtime/onboard/hosts.ini <<'EOF'
[vps_targets]
vps-a ansible_host=<VPS_A_IP> ansible_user=<BOOTSTRAP_USER> ansible_port=22 ansible_ssh_private_key_file=~/.ssh/ansispire_ansible ansible_python_interpreter=/usr/bin/python3
EOF

# 2.5 — managed inventory: used AFTER onboard, when SSH has moved to ansible@39222
cat > runtime/onboard/hosts.managed.ini <<'EOF'
[vps_targets]
vps-a ansible_host=<VPS_A_IP> ansible_user=ansible ansible_port=39222 ansible_ssh_private_key_file=~/.ssh/ansispire_ansible ansible_python_interpreter=/usr/bin/python3
EOF

# 2.6 — onboard task payload. The managed authorized key is the same fleet key
#        used by the playbook transport; no managed private-key path is in vps_task.
cat > runtime/onboard/vps-a.yml <<'EOF'
---
vps_task:
  bootstrap:
    host: <VPS_A_IP>
    port: 22
    user: <BOOTSTRAP_USER>
  managed:
    user: ansible
    groups:
      - sudo
    shell: /bin/bash
    authorized_keys:
      - public_key: ~/.ssh/ansispire_ansible.pub
    sudo:
      nopasswd: true
  ssh:
    managed_port: 39222
    disable_root_login: true
    disable_password_login: true
    disable_kbd_interactive: true
    close_bootstrap_port_after_success: false   # keep 22 open until verified; flip to true in Phase 5
  profile:
    base_packages: true
    unattended_upgrades: true
    system_limits: true
  packages:
    install: [curl, vim, sudo, ufw, fail2ban, unattended-upgrades, git, htop]
    remove: []
  firewall:
    default_incoming: deny
    default_outgoing: allow
    allowed_tcp_ports: [39222]
    allow_http_https: false
  fail2ban:
    enabled: true
EOF

# 2.7 — docker task payload (installed in Phase 4 via docker_host.yml, official apt repo)
cat > runtime/onboard/docker.yml <<'EOF'
---
vps_task:
  docker:
    install: true
    install_method: official_apt_repo
    add_managed_user_to_docker_group: true   # ansible user can run docker without sudo (== root-equiv; be aware)
    compose_plugin: true
    enable_ipv6: false
    logging:
      driver: json-file
      max_size: 50m
      max_file: 3
  firewall:
    manage_docker_user_chain: true
EOF
```

Then fill in the `<...>` placeholders in `hosts.ini`, `hosts.managed.ini`, and `vps-a.yml`.

## Phase 3 — Onboard

```bash
# 3.1 — confirm the fleet key reaches the bootstrap channel.
ssh -i ~/.ssh/ansispire_ansible <BOOTSTRAP_USER>@<VPS_A_IP> true

# 3.2 — OPEN PORT 39222 in the cloud provider's security group (keep 22 open too),
#        otherwise onboard's `wait_for 39222` will time out after the SSH switch.

# 3.3 — dry-run (--ask-become-pass: the bootstrap user's sudo needs a password)
ansible-playbook playbooks/vps/onboard.yml \
  -i runtime/onboard/hosts.ini -e @runtime/onboard/vps-a.yml \
  --check --diff --ask-become-pass

# 3.4 — real run
ansible-playbook playbooks/vps/onboard.yml \
  -i runtime/onboard/hosts.ini -e @runtime/onboard/vps-a.yml \
  --ask-become-pass

# 3.5 — verify the managed channel (ansible@39222, key has no passphrase → no agent needed)
ssh -i ~/.ssh/ansispire_ansible -p 39222 ansible@<VPS_A_IP> sudo -n true && echo "OK: managed channel up"
```

> **GOTCHA 2 — dry-run (`--check`) fails at "Install managed user authorized keys"**
> with *"Either user must exist ... in check mode"*. This is a check-mode
> limitation, **not** a config error: under `--check` the managed user isn't
> actually created, so the next task can't resolve its home. The real run
> creates the user and this step passes. Dry-run leaves **no** side effects on
> the target (verified: no user / no packages created).

> **GOTCHA 3 — `[WARNING] ... /root/.ansible/tmp ...`** is expected. Tasks run
> `become: true`, so after logging in as `<BOOTSTRAP_USER>` ansible escalates to
> root to make system changes; the remote temp dir is therefore under root's
> home. Login user = `<BOOTSTRAP_USER>`, execution user = root. Harmless.

> **Safety**: with `close_bootstrap_port_after_success: false`, both 22 and 39222
> stay open and lockdown of root/password login only completes after the
> sudo-validation step. Keep the provider's VNC/console available as a fallback.

## Phase 4 — Install Docker

```bash
# onboard moved SSH to ansible@39222, so use the managed inventory now.
# ansible user has nopasswd sudo + passphrase-less key → no --ask-* flags needed.
ansible-playbook playbooks/vps/docker_host.yml \
  -i runtime/onboard/hosts.managed.ini -e @runtime/onboard/docker.yml --check --diff
ansible-playbook playbooks/vps/docker_host.yml \
  -i runtime/onboard/hosts.managed.ini -e @runtime/onboard/docker.yml

# verify
ssh -i ~/.ssh/ansispire_ansible -p 39222 ansible@<VPS_A_IP> 'docker --version && docker compose version'
```

Docker is intentionally **not** part of onboard — `docker_host.yml` installs
Docker CE + the compose plugin from Docker's official apt repo (not the distro's
old `docker.io`).

## Phase 5 — Finalize (close the bootstrap port)

Only after Phases 3–5 verifications pass:

```bash
sed -i 's/close_bootstrap_port_after_success: false/close_bootstrap_port_after_success: true/' runtime/onboard/vps-a.yml

# connection still goes via <BOOTSTRAP_USER>@22 with the fleet key
ansible-playbook playbooks/vps/onboard.yml \
  -i runtime/onboard/hosts.ini -e @runtime/onboard/vps-a.yml \
  --ask-become-pass
```

After this the only entry is `ansible@39222` with fleet-key auth; root login and
password login are disabled and port 22 is closed in ufw.

---

## Phase 6 — Register the host into Semaphore (converge the entry points)

The host is now managed but only known to your local `runtime/onboard/*.ini`
files. Add it to Semaphore's `vps-fleet` static inventory so the active audit
template sees the managed channel:

```ini
[vps_targets]
vps-a ansible_host=<VPS_A_IP> ansible_user=ansible ansible_port=39222
```

`vps-fleet` is already bound to `vps-fleet-key`, so the same fleet private key
drives the managed connection. Run `VPS Audit` and require `success` with
`changed=0`; `make controller-vps-smoke` repeats that assertion later. The
Worker register/onboard paths are deferred and are not required for this flow.

## Connection password reference (don't conflate the three)

| Which password | What it unlocks | How it's supplied |
|----------------|-----------------|-------------------|
| SSH key passphrase | decrypts your private key | `ssh-agent` + `ssh-add` (once) |
| SSH login password | password auth, if the server requires it on top of the key | `--ask-pass` (needs `sshpass`) |
| sudo / become password | privilege escalation for the bootstrap user | `--ask-become-pass` |

## Known project gaps surfaced during this run (follow-ups, not blockers)

1. `ansible.cfg` global `vault_password_file` makes a fresh clone fail on *all*
   ansible commands until `.vault_pass` exists (Phase 0 GOTCHA 1).
2. `onboard.yml` can't be fully dry-run under `--check` (authorized_key step)
   (Phase 3 GOTCHA 2).
3. `requirements.txt` uses `>=` lower bounds → version drift (e.g. core 2.21.0);
   tracked under TASK-009.
