## §1. Purpose / Scope

### Purpose
Remove AlmaLinux from Ansispire's supported platform matrix. The RHEL family is henceforth **Rocky Linux 9+ only**. Ensure the Rocky/RHEL sudo admin group is `wheel` everywhere it is set — including the standalone `onboard.yml` path that currently defaults to `sudo`.

### In scope
1. **Passive removal** of AlmaLinux from the support matrix, Tier-1 lists, role `meta` platforms, and all *current* truth-source docs.
2. **Remove the two Alma host records** (`alma9` in `inventory/hosts.ini`; `hk-alm9` in the vps_runner dev inventory + its `host_vars` file, which carries a `failed` last_run).
3. **`onboard.yml` wheel fix**: family-select the managed admin group (`wheel` for RedHat, `sudo` for Debian) instead of hardcoding `['sudo']`.
4. **Sync Guard** (project §0): update ARCHITECTURE / README / feature-map(s) / INDEX / CHANGELOG `[Unreleased]`.

### Out of scope
- Physical decommission of the AlmaLinux VPS (82.152.164.144) — user's manual action.
- Active rejection of AlmaLinux at runtime (user chose passive removal; the shared RHEL path stays tolerant).
- Rewriting historical changelogs / archived reviews / `reference-cn` snapshots — those are immutable records of what happened.
- Any change to Debian/Ubuntu or Alpine handling.

### Judgment criteria (done = all true)
- `grep -rni alma` over **active** code + current docs returns nothing (archives/snapshots/historical changelogs excluded).
- `ansible-lint` + `yamllint` clean on changed files.
- `ansible-playbook --syntax-check` passes for `onboard.yml` and `playbooks/deploy_target.yml`.
- A dry-run / `--check` (or fact-trace) confirms the managed admin group resolves to `wheel` on a RedHat host and `sudo` on a Debian host.
- Truth sources (ARCHITECTURE / README / feature-map / INDEX / CHANGELOG) consistently state Rocky-only.

## §4. Decision rationale (per change class)

- **Passive, not active reject** (user decision): Rocky & Alma are binary-compatible RHEL 9; the role path keys on `os_family == RedHat`. Adding a distribution-level fail would reject a working distro for no functional reason and add a code branch to maintain. Removing Alma from the *documented + tested + inventoried* set is the minimal, honest expression of "we no longer support it."
- **`onboard.yml` family-select admin group**: mirrors the established `roles/infra_baseline` pattern (`defaults: sudo` + `vars/RedHat.yml: wheel`). Inline conditional because `onboard.yml` is standalone. Idempotent: `wheel` already exists on RHEL, so the group task is a no-op there; the user is appended to `wheel` not `sudo`.
- **Delete `hk-alm9.yml`**: it holds a `failed` last_run for a host we're dropping; keeping it would leave a dangling target the wizard/list could surface.
