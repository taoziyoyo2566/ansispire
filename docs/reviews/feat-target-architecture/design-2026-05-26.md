## 一、项目定位

**Ansispire = Semaphore（控制平面）+ VPS 内容库 + EDA 自愈平面 + Wizard UX**

Semaphore 负责：持久化、调度、历史记录、RBAC、SSH 密钥管理。  
Ansispire 负责 Semaphore 做不了的：VPS 生命周期自动化内容、事件驱动自愈、结构化录入体验。

| 层 | 组件 | 来源 |
|---|---|---|
| 控制平面 | Semaphore | 上游 OSS，直接使用 |
| 接入层 | CF Worker（wizard）+ CF Tunnel | Cloudflare 托管，零维护 |
| 执行层 | playbooks / roles | Ansispire 核心内容 |
| 事件层 | audit-relay / sink / reactor | Ansispire 自建 EDA 平面 |

---

## 二、架构全图

```
浏览器
  │ HTTPS
  ▼
CF Worker                         ← wizard 表单 + 参数校验 + API proxy
  │ CF Tunnel（出站，零入站端口）   ← Semaphore API token 存 Worker env secret
  ▼
Semaphore（localhost:3300）
  ├── Inventory（static 类型）      ← 主机连接信息，唯一 source of truth
  ├── Key Store                    ← SSH 私钥，加密存储
  ├── Task API                     ← 触发 onboard / modify / audit / remove
  ├── Schedule                     ← audit 定期自动运行
  └── RBAC / Job History
  │ ansible-runner（内置）
  ▼
playbooks/vps/                     ← 保留的 lifecycle playbook
  ├── onboard.yml
  ├── modify.yml
  ├── audit.yml
  └── remove.yml
roles/ group_vars/                 ← 策略配置，git 管理，不进 DB
  │ 执行结果 → events.jsonl
  ▼
EDA 平面
  audit-relay  → 拉取 Semaphore 事件
  audit-sink   → 持久化结构化事件
  audit-reactor→ 规则匹配 → 触发 Task API 自愈
```

## 三、关键设计决策

### 3.1 Semaphore Inventory 类型：当前目标仍是 `static`

`IVG-SEMAPHORE-INVENTORY-API` 静态调查表明，当前公开契约里的 inventory 类型不止两种，至少包括：

| 类型 | 存储位置 / 语义 | 适用场景 |
|---|---|---|
| `file` | 指向 repo / repository 中的 inventory 文件 | 继续把 inventory 真相放在 git |
| `static` | inventory 文本存数据库（当前目标：INI 风格） | **DB 作为 source of truth**（本方案） |
| `static-yaml` | inventory 文本存数据库（YAML 风格） | 若后续决定改用 YAML inventory |
| `constructed` | 由 repository 内规则构造 inventory | 当前不是首选 |

对 ansispire 当前保留资产来说，目标架构仍优先使用 `static`，因为现有 inventory / playbook 约定是 INI 风格、且需要保留 `vps_targets` 这类分组语义。当 task 运行时，Semaphore 会把 DB 中的 inventory 内容写入临时文件并以 `-i <tempfile>` 交给 Ansible，**Ansible 无需任何额外的 dynamic inventory 脚本**。

当前项目 `bootstrap.yml` 使用的是 `file` 类型（指向 `inventory/prod/hosts.ini`），迁移时需要新建 DB-backed inventory 对象，而不是继续依赖 repo 内文件。

### 3.2 Inventory blob 的读改写模型

当前公开契约仍然更像“整份 inventory 对象 CRUD”，而不是 per-host CRUD。对本方案而言，应暂按**整份 blob 读改写**建模：

```
GET /api/project/{id}/inventory/{inv_id}  →  读取当前 inventory 对象
解析 inventory 文本（当前目标：INI） → 修改 hosts / vars / groups
PUT /api/project/{id}/inventory/{inv_id}  →  写回完整对象
```

**已知风险**：两个并发写操作会互相覆盖（last-write-wins）。  
**可接受原因**：单租户使用场景，并发写极罕见。多租户场景需要加写锁或乐观并发控制，届时再处理。

> **待验证（Phase 1）**：
> 1. `GET /inventory/{id}` 的响应体是否直接包含完整 inventory 文本
> 2. `PUT /inventory/{id}` 是整对象 replace 还是更细粒度语义
> 3. `static` 与 `static-yaml` 在当前镜像版本下的实际字段差异

### 3.3 变量分层：连接信息 vs 策略配置

当前主线 `vps_manager` 方案把长期状态分散在多个本地载体里：

| 类别 | 当前载体 | 目标存储位置 |
|---|---|---|
| 连接信息 | `runtime/state/vps_inventory.yml`、生成的 SSH config | Semaphore Inventory blob |
| 凭据 / 密钥 | `runtime/keys/`、运行时环境变量注入 | Semaphore Key Store |
| 策略 / 配置 | task payload 里的可选项、role/group vars | `group_vars/`（git 管理） |
| 运行元数据 | `pending/processing/done/failed/archived` 任务记录、本地状态字段 | Semaphore Job History / Schedule / Task history |

迁移后，playbook 不再依赖本地 runtime 维护的服务器事实；连接信息由 Ansible inventory 机制提供，策略配置保留在 git 管理的 `group_vars/` / roles 默认值中。

### 3.4 首次上线（first-time onboard）的处理

首次上线需要用 bootstrap user/port 连接（root@22），而不是管理通道（ansible@1156）。

**本节在 2026-06-03 经 `IVG-SEMAPHORE-INVENTORY-API` 静态调查校正：当前还不能把“Task API 稳定支持 `extra_vars`”写成既定事实。**

当前分支里保留的生命周期 playbook 已经固定要求顶层 `vps_task` 结构，因此 Wizard / Worker 的设计目标也应围绕 `vps_task.bootstrap` 组包，而不是继续扩展零散的 `vps_first_time_*` 顶层变量。例如：

```yaml
vps_task:
  bootstrap:
    host: 203.0.113.10
    port: 22
    user: root
    auth:
      method: password
      password_env: VPS_BOOTSTRAP_PASSWORD
```

首次上线参数的候选承载路径（待 Phase 1 运行态验证）：

1. Task API 直接接受额外运行参数，并能映射到 `vps_task`
2. Template survey vars / 其他 Semaphore 任务参数机制承载 `vps_task`
3. 如果以上都不成立，则由 Worker 侧承担更显式的模板 / 参数适配层

在这件事跑通之前，不把“`POST /api/project/{id}/tasks` 直接传 `extra_vars`”当成当前分支的已确认事实。无论最终承载路径是哪一种，上线成功后 inventory 中都只保留管理通道的连接信息。

### 3.5 SSH 私钥流转路径

```
浏览器（wizard 表单输入 PEM）
  ↓ HTTPS POST 到 CF Worker
CF Worker 内存（不落盘）
  ↓ POST /api/project/{id}/keys
Semaphore Key Store（加密存储在 SQLite volume）
  ↓ task 运行时解密注入
Ansible SSH 连接
```

私钥不经过任何文件系统，CF Worker 内存是唯一的中间态。Cloudflare 基础设施的可信度与自托管 VPS 相当。

### 3.6 Ansible Collection 依赖的容器化

Semaphore 官方镜像不预装 `community.general`、`ansible.posix` 等 collection。解决方案：

**推荐**：基于官方镜像自定义 Dockerfile，烘焙 `requirements.yml`：
```dockerfile
FROM semaphoreui/semaphore:latest
RUN ansible-galaxy collection install -r /requirements.yml
COPY requirements.yml /requirements.yml
```

- 优点：运行时零外部依赖，启动确定性高
- 代价：Semaphore 升级时需重建镜像（可在 CI 中自动化）

备选：compose entrypoint 启动时动态安装，collection 存 volume。适合开发环境，不推荐生产。

## 四、部署形态

### 服务器侧（一条命令）

```bash
docker compose up
```

| 容器 | 说明 |
|---|---|
| `ansispire-semaphore` | 自定义镜像（含 Ansible + collections） |
| `audit-reactor` | EDA 规则引擎 |
| `audit-relay` | Semaphore 事件拉取转发 |
| `audit-sink` | 事件持久化 |
| `cloudflared` | CF Tunnel 出站连接，零入站端口 |

### Cloudflare 侧（一次性）

```bash
wrangler deploy    # 部署 CF Worker
```

CF Tunnel 域名绑定在 Cloudflare 控制台配置一次，后续无需操作。

## 五、废弃内容

| 废弃项 | 理由 | 替代 |
|---|---|---|
| `plugins/vps_manager/cli.py` | 本地 task inbox / generator 不再是控制面入口 | CF Worker + Semaphore Task API |
| `plugins/vps_manager/vps_manager.py` | inventory / key / task history 由 Semaphore 接管 | Semaphore Inventory + Key Store + Task API |
| `runtime/inbox/vps/*` | 本地 inbox 不再作为任务 source of truth | Semaphore Task API |
| `runtime/state/vps_inventory.yml` | 主机连接信息进 Semaphore DB | Semaphore `static` inventory |
| `runtime/keys/` 临时密钥文件 | 密钥进 Semaphore Key Store | Semaphore Key Store |
| `docs/operations/vps-manager.md` 等 `vps_manager` 专属文档 | cutover 后不再是主入口 | Semaphore-centric operator / user docs |

playbooks / roles / group_vars **保留不动**。

## 六、已知风险与未解问题

| 问题 | 性质 | 处理方式 |
|---|---|---|
| `GET /inventory/{id}` 是否返回 blob content | **Phase 1 必须验证**，否则 CF Worker 无法实现读改写 | Phase 1 Session 1 调用 API 确认 |
| Inventory blob 并发写冲突 | 单租户可接受，多租户需加锁 | 当前忽略，多租户触发时处理 |
| bootstrap user/port 的临时存储 | 首次上线失败后重试需要重新填写 | 可在 CF Worker 中用 session/cookie 暂存，不持久化 |
| Semaphore 镜像升级时需重建自定义镜像 | 维护成本 | CI 自动化构建；或接受短暂的手动操作 |
| CF Worker Python runtime beta 稳定性 | 若选 Python | 建议选 JS（稳定）；Python 留作备选 |

## 七、实施顺序

```
Phase 1  Semaphore Inventory API 调研
         → 验证 GET content 字段、static 类型写入、task extra_vars 行为
         → 输出：IVG-SEMAPHORE-INVENTORY-API.md

Phase 2  CF Worker 搭建
         → 路由框架（itty-router）+ Semaphore API client + wizard 表单
         → 前置：Phase 1 完成 + 语言选型（JS 推荐）
         → 门控：wizard 新增 VPS，Semaphore UI 可见

Phase 3  vps_manager 废弃 + 本地 runtime 迁移
         → 已完成 owner-branch cleanup：删除 vps_manager Python 层和本地 runtime 事实来源，playbook 迁到 `playbooks/vps/`
         → 后续继续把现有 VPS 连接状态迁入 Semaphore static inventory / Key Store
         → 清理剩余不再相关的 vps_manager 文档
         → 验证 playbook 变量路径兼容（连接信息走 inventory，策略走 group_vars）
         → 门控：对真实节点跑 onboard + audit 全流程

Phase 4  生产硬化（待 Q1-Q3 决策）
         → 自定义 Semaphore Dockerfile（烘焙 collections）
         → cloudflared 加入 compose
         → DB 备份策略（Q2）
         → 内部服务 TLS 评估（Q1）

Phase 5  长期演进（触发条件驱动，不预先规划）
         → ansible-rulebook 迁移：rules ≥ 5 条且需多事件聚合
         → OSS Runner 引入：fleet ≥ 2 真实分组且并发达瓶颈
         → 多租户：开放给其他团队 self-service
```
