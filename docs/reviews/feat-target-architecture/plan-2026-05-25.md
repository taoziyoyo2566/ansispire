## §1. 目标定义

### 1.1 这个项目是什么

**Ansispire = Semaphore（基础设施层）+ VPS 内容库 + EDA 平面 + Wizard UX**

Semaphore 做它擅长的：持久化、调度、历史记录、RBAC。
Ansispire 只做 Semaphore 做不了的：VPS 自动化内容、事件驱动自愈、更好的录入体验。

### 1.2 与裸 Semaphore 的对比

**Semaphore 提供，Ansispire 直接使用：**

| 能力 | 使用方式 |
|---|---|
| Inventory 持久化 | 主机连接信息存 Semaphore DB，通过 API 管理 |
| Key Store | SSH 私钥存 Semaphore，不落本地文件系统 |
| Task API | CF Worker 触发 onboard / modify / audit / remove |
| Job history | 所有操作记录自动留存，可审计 |
| RBAC | owner / manager / task_runner / guest 四角色 |
| 定时任务（Schedule） | audit 定期自动运行，无需手动触发 |

**Ansispire 在 Semaphore 之上增加的：**

| 增量 | 内容 | Semaphore 有没有 |
|---|---|---|
| VPS 生命周期 playbook | onboard / modify / audit / remove | ❌ Semaphore 只是执行器 |
| 安全加固 roles | infra_baseline（SELinux / firewalld / fail2ban）、common/security.yml（SSH 加固 / sudoers） | ❌ |
| EDA 平面 | audit-relay → audit-sink → audit-reactor → 自愈闭环 | ❌ |
| 合规审计规则 | 项目级 VPS 配置合规检查与巡检逻辑 | ❌ |
| Wizard UX | CF Worker 弥补 Semaphore blob 编辑器的不足，提供表单化录入 | ❌ |

### 1.3 完整数据流

```
┌─────────────────────────────────────────────────────┐
│  录入层（VPS 新增 / 变更）                           │
│                                                     │
│  浏览器 Wizard                                       │
│    ↓ HTTPS                                          │
│  CF Worker（表单校验 + API proxy）                   │
│    Semaphore API token 存 Worker env secret          │
│    ↓ CF Tunnel（零入站端口）                         │
│  Semaphore:3300（localhost）                         │
└─────────────────────────┬───────────────────────────┘
                          │
┌─────────────────────────▼───────────────────────────┐
│  持久化层（Semaphore，唯一 source of truth）          │
│                                                     │
│  Inventory  ← 主机连接信息（IP / 端口 / 用户）       │
│  Key Store  ← SSH 私钥                              │
│  Task API   ← 触发执行                              │
│  Job History / Schedule / RBAC                      │
└─────────────────────────┬───────────────────────────┘
                          │ ansible-runner（Semaphore 内置）
┌─────────────────────────▼───────────────────────────┐
│  执行层（Ansispire 核心内容，保持不动）               │
│                                                     │
│  playbooks/vps/  onboard.yml / modify.yml           │
│                 audit.yml / remove.yml              │
│  roles/      infra_baseline / common / ...          │
│  group_vars/ 策略配置（git 管理，不进 DB）           │
└─────────────────────────┬───────────────────────────┘
                          │ 执行结果写入 Semaphore events.jsonl
┌─────────────────────────▼───────────────────────────┐
│  EDA 平面（事件驱动自愈）                            │
│                                                     │
│  audit-relay  → 拉取 Semaphore 事件写入 jsonl        │
│  audit-sink   → 接收并持久化结构化事件               │
│  audit-reactor→ 匹配规则 → 触发 Task API 自愈        │
└─────────────────────────────────────────────────────┘
```

**数据分层：**

```
git              → playbooks / roles / group_vars（how to configure）
Semaphore SQLite → 主机 inventory + SSH 密钥（what servers exist, how to reach them）
CF Worker secret → Semaphore API token（不落任何文件）
```

## §2. 已确定结论

### 2.1 VPS 管理层重构

| 决策 | 结论 | 取代什么 |
|---|---|---|
| Inventory 持久化 | Semaphore SQLite（通过 API 管理） | `runtime/state/vps_inventory.yml` 与本地生成的连接信息副本 |
| SSH 密钥存储 | Semaphore Key Store | `runtime/keys/` 临时密钥 + `ansible_ssh_private_key_file` |
| VPS 操作触发 | Semaphore Task API | `vps_manager` 本地 task inbox + `process` 调度 |
| 策略配置（audit rules / features） | 留 `group_vars`（git 管理） | 不进数据库 |
| `vps_manager` Python 插件层 | **废弃**（`cli.py` + `vps_manager.py`） | — |
| playbooks（onboard/modify/audit/remove） | **保留不动** | 这是核心价值，路径不变 |

**废弃原因**：当前 `vps_manager` 本地调度层存在的根本原因，是缺少一个统一的控制平面来持久化 inventory、密钥和任务历史。Semaphore 接管这些职责后，再保留一套本地 runtime / inbox / state 只会制造第二套 source of truth。历史上的 `feat/vps-manager-v2`（`vps_runner` 尝试）保留作参考，但不是这条方向的 owner。

### 2.2 用户交互层

| 决策 | 结论 |
|---|---|
| Wizard UI 实现 | CF Worker（不 fork Semaphore） |
| 公网访问入口 | CF Tunnel 绑定 `127.0.0.1:3300`，Semaphore 不开放入站端口 |
| SSH 私钥流转 | 浏览器 → CF Worker 内存 → Semaphore Key Store，不落盘 |
| Semaphore API token | 存 CF Worker env secret，浏览器不可见 |
| Semaphore UI 的 inventory 管理 | 仅文本 blob 编辑器，无表单，不满足需求 → CF Worker 补位 |

**为什么不 fork Semaphore**：Semaphore 是 Go + Vue.js，没有插件系统，维护自己的分支意味着每次上游版本都要人工 merge，POC 阶段成本不可接受。

### 2.3 控制平面架构（WU-5 结论直接引用）

| 决策 | 结论 | 重启 IVG 的触发条件 |
|---|---|---|
| reactor 是否迁移 ansible-rulebook | **否（当前）** | rules ≥ 5 条且需多事件聚合；或需接入 alertmanager/kafka 等非 jsonl 源；详见 IVG-EDA-RULEBOOK-MIGRATION §6.1 |
| 是否引入 OSS Runner 拆分 | **否（当前）** | fleet ≥ 2 真实分组且 job 并发达瓶颈；或出现 executor 拖死 controller P2 issue；详见 IVG-EXECUTION-PLANE-RUNNER §6.1 |

### 2.4 用户模型与 RBAC

| 决策 | 结论 |
|---|---|
| 当前租户模型 | 单租户 |
| 多租户规划时间线 | 不强求，触发条件为"开放给其他团队 self-service"时再起 IVG |
| Semaphore RBAC 四角色模型 | 保留（Round 8 已验证：owner/manager/task_runner/guest） |
| 多租户实现路径 | CF Worker 加 auth layer + Semaphore 多 project 隔离（Phase 5，触发条件驱动） |

## §6. 完全 Docker 化部署可行性

### 6.1 结论

**可行，且大部分已经是了。** 目标状态下一条 `docker compose up` 拉起服务器侧所有组件，`wrangler deploy` 部署 CF Worker 侧。

### 6.2 各组件容器化状态

| 组件 | 状态 | 说明 |
|---|---|---|
| Semaphore | ✅ 已有 | `controller/semaphore/docker-compose.yml` |
| audit-reactor / relay / sink | ✅ 已有 | `controller/audit/docker-compose.yml` |
| Ansible 执行环境 | ✅ 内置 | Semaphore 镜像包含 Ansible，repo 以只读 volume 挂入 |
| cloudflared（tunnel 客户端） | ⬜ 待补 | 官方提供 Docker 镜像，加一个 compose service 即可 |
| CF Worker（wizard UI） | 不适用 | 运行在 Cloudflare 边缘节点，`wrangler deploy` 部署，非自托管容器 |

### 6.3 Ansible 运行方式

Ansible 在 Semaphore 容器内部执行，通过 SSH 连接远端 VPS，SSH 私钥由 Key Store 解密后注入执行环境。不需要独立的 Ansible 容器。

```
Semaphore 容器
  → ansible-playbook onboard.yml（容器内）
  → SSH → 远端 VPS（出口 IP = 服务器公网 IP）
```

### 6.4 唯一未解决的依赖：Ansible Collection

`roles/` 依赖 `community.general`、`ansible.posix` 等 collection（见 `requirements.yml`）。Semaphore 镜像不预装这些，需要选一种方式解决：

| 选项 | 方式 | 优劣 |
|---|---|---|
| **A（推荐）** | 基于 Semaphore 镜像自定义 Dockerfile，烘焙 `requirements.yml` | 运行时零依赖；升级 Semaphore 版本时需重建镜像 |
| B | compose entrypoint 启动时跑 `ansible-galaxy install`，collection 存 volume | 无需维护自定义镜像；每次启动多几秒，网络不稳定时有风险 |

**选项 A 是 Phase 4 的一项工作**，与生产硬化一并处理。

### 6.5 最终部署形态

```
服务器（一条命令）：
  docker compose up
    → ansispire-semaphore（含 Ansible + collections）
    → audit-reactor / relay / sink
    → cloudflared（tunnel 出站连接）

Cloudflare 侧（一次性）：
  wrangler deploy
    → CF Worker（wizard UI，托管在 CF 边缘）
  CF Tunnel 域名绑定（控制台配置一次）
```
