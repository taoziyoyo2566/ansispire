## Scope

2. Verify the task-launch mechanism that carries nested `vps_task` into Ansible.
3. Update design / investigation docs so Phase 2 can begin from runtime evidence instead of an `extra_vars` stub.

## Runtime Results

| Probe | Result | Evidence |
|---|---|---|
| `GET /api/project/1/inventory/2` on current `targets-managed` | `200`; full object returned; current type is `file`; `.inventory` is `inventory/hosts.ini` | User shell output, 2026-06-06 |
| `POST /api/project/1/inventory` with `type: "static"` | `201`; INI blob persisted verbatim | temporary inventory `id=3` |
| `GET /api/project/1/inventory/3` | `200`; `.inventory` is the INI blob | temporary inventory `__probe_static_inventory__` |
| `PUT /api/project/1/inventory/3` | `204`; follow-up GET showed replacement blob | `probe` changed to `probe2` |
| `POST /api/project/1/tasks` with raw `extra_vars` | `201`, but not proven to reach Ansible | task `id=1`; output showed normal ping run and no `vps_task` evidence |
| `POST /api/project/1/tasks` with task-level `environment` JSON string | `201`; task detail preserved the string; Ansible debug received nested `vps_task` | task `id=2`, output included `vps_task.source = task-environment-field` |

---

## Conclusions

- Inventory CRUD direction is confirmed: Worker should use `static` inventory, read-modify-write the whole INI blob, and expect `PUT` to return `204`.
- Raw `extra_vars` is not a supported Worker contract. It may be accepted as an unknown field, but the probe did not prove it reaches Ansible.
- Task-level `environment` is the confirmed runtime payload path for nested `vps_task`.
- Phase 2 Worker implementation is no longer blocked by the Phase 1 runtime probe.
