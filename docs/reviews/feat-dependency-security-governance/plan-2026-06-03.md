## §0. Purpose

Close the gap between the project's current **version governance skeleton** and a real **security / compatibility audit loop**.

Today the repo already has:
- a version SSOT for container tags (`config/manifest.yml`)
- a pinned baseline for the local Ansible toolchain
- `detect-secrets`
- Dependabot for `pip` + GitHub Actions
- a Semaphore API drift gate (`make test-api-contract`, pinned + latest)

But it does **not** yet provide a defensible answer to questions like:
- "Are any current Python packages or container images known-vulnerable?"
- "Is the pinned Semaphore version still an acceptable upstream security target?"
- "Do we know which dependency set / image set is actually supported together?"
- "What is the merge gate when a critical CVE exists but a fix is not yet adopted?"

This plan defines the future work needed to make those answers explicit.

## §2. Current-State Assessment

### 2.1 What already exists

| Surface | Current truth |
|---|---|
| Container image tags | `config/manifest.yml` is the SSOT |
| Local Python toolchain baseline | `Ansible-Core 2.20.5` is the pinned baseline |
| Secret scanning | `detect-secrets` is part of `make verify` / CI |
| Semaphore upgrade drift | `make test-api-contract` runs pinned + latest matrix |
| Dependency auto-bumps | Dependabot covers `pip` + `github-actions` |

### 2.2 What is still missing

| Gap | Why it matters |
|---|---|
| No Python vulnerability scan | `requirements.txt` / `pyproject.toml` can drift into known-vulnerable ranges without a merge blocker |
| No image vulnerability scan | `semaphoreui/semaphore`, `python:3.12-alpine`, and baked audit images have no CVE gate |
| No lock / release-mode dependency freeze | current manifests are mostly `>=` minimums, not a reproducible release set |
| No supported-version compatibility matrix | "works on my machine" is not the same as "supported together" |
| No explicit Semaphore upstream watch policy | pinned version can become stale without a review ritual |
| No security exception / waiver mechanism | merge decisions become ad hoc under pressure |

### 2.3 Explicit non-goal of the current system

The current project can answer:
- "Do the known tests pass?"
- "Did the Semaphore API shape drift?"
- "Did someone commit a secret literal?"

It cannot yet answer:
- "Is this stack free of known High/Critical CVEs?"
- "Is this exact dependency / image set our approved release set?"

---

## §3. End State

This workstream is complete when the repo has a documented, repeatable way to assert all of the following:

1. **Version truth**
   - Every dependency / image surface has one declared owner source.
   - Release-mode versions are reproducible, not reconstructed from loose lower bounds.

2. **Vulnerability truth**
   - Python dependencies and container images are scanned in CI.
   - Findings have severity thresholds and a waiver path.

3. **Compatibility truth**
   - There is a published "supported set" for local toolchain + main images.
   - Candidate upgrades have a defined verification matrix before adoption.

4. **Semaphore upstream truth**
   - Bumping `semaphore_pinned` requires release / advisory review and local contract verification.

5. **Operator truth**
   - Future agents know what to check, when to fail, and when a human waiver is required.

## §4. Work Units

### WU-1 — Version Truth & Release Freeze Model
**Branch**: `feat/dependency-security-governance`
**Goal**: define what is "minimum development floor" vs "release-approved resolved set".

**Scope**
- classify all versioned surfaces:
  - local Python toolchain
  - Ansible collections
  - Semaphore image
  - upstream Python base image
  - baked audit images
- define two modes:
  - **dev floor**: current `>=` style minimums remain acceptable for contributor setup
  - **release freeze**: add a reproducible resolved set for release / audit
- choose the freeze carrier:
  - `uv.lock`
  - compiled constraints file
  - explicit release manifest
  - image digests for container releases

**Deliverables**
- `docs/governance/dependency-security.md`
- one repo-native resolved-set artifact for release mode
- documentation clarifying which file is SSOT for each surface

**Open decision**
- whether release freeze should apply only to CI / release or also to all local development

---

### WU-2 — Vulnerability Scanning Gates
**Branch**: `feat/dependency-vuln-gates`
**Goal**: add actual SCA / CVE coverage.

**Scope**
- Python dependency scan
  - candidate tools: `pip-audit` or `osv-scanner`
- Container image scan
  - candidate tools: `trivy` or `grype`
- define scan targets:
  - local Python dependency set
  - `semaphoreui/semaphore:${SEMAPHORE_IMAGE_TAG}`
  - `python:${AUDIT_PYTHON_BASE_TAG}`
  - baked `ansispire/audit-*` images
- define merge thresholds:
  - fail on `High` / `Critical` by default
  - configurable exceptions via waiver file

**Deliverables**
- new make targets, e.g. `make scan-vulns-python`, `make scan-vulns-images`
- CI jobs for vulnerability scans
- machine-readable report artifacts

**Important boundary**
- findings must distinguish:
  - direct dependency
  - transitive dependency
  - base image package
  - unfixed upstream CVE

---

### WU-3 — Compatibility Matrix & Upgrade Verification
**Branch**: `feat/compatibility-matrix`
**Goal**: replace fuzzy "should be compatible" with a declared supported matrix.

**Scope**
- define supported combinations for:
  - local Python / Ansible toolchain
  - Semaphore image
  - audit Python base image
- define what "compatible" means:
  - `make verify` passes
  - `make test-api-contract` passes
  - selected e2e / smoke gates pass
- define candidate-upgrade workflow:
  - read upstream release notes
  - run matrix verification
  - record results in changelog

**Deliverables**
- `docs/reference/compatibility-matrix.md`
- a branch / PR checklist for version bumps
- optional CI matrix expansion for candidate versions

**Key rule**
- "Perfect compatibility" is not a valid claim.
- Only "supported", "candidate", "waived", or "unsupported" are valid states.

---

### WU-4 — Semaphore Upstream Security Policy
**Branch**: `feat/semaphore-security-policy`
**Goal**: make Semaphore version bumps security-aware, not just syntax-aware.

**Scope**
- define a required review set before changing `semaphore_pinned`:
  - upstream release notes
  - security advisories / CVE search
  - API contract gate
  - local smoke / e2e expectations
- encode hard requirements for security-sensitive envs:
  - `SEMAPHORE_ACCESS_KEY_ENCRYPTION`
  - `SEMAPHORE_COOKIE_HASH`
  - `SEMAPHORE_COOKIE_ENCRYPTION`
  - no plaintext-exposed production path
- add a maintainer checklist for "adopt / hold / waive" decisions on new releases

**Deliverables**
- `docs/governance/semaphore-upgrade-policy.md`
- CI or review-template enforcement for Semaphore image tag changes

---

### WU-5 — Waiver, Cadence, and Audit Closure Rules
**Branch**: `feat/security-waiver-governance`
**Goal**: prevent endless scanning noise and ad hoc exceptions.

**Scope**
- define a waiver file / schema:
  - finding id
  - affected surface
  - severity
  - rationale
  - expiry date
  - owner
- define audit cadence:
  - per PR gates
  - scheduled weekly / monthly scan
  - release-before-cut scan
- define closure rules:
  - when a scan is considered "green enough"
  - when a waiver is mandatory
  - when merge must stop

**Deliverables**
- `docs/governance/security-waivers.md`
- waiver artifact template
- review wording for PR / release closure

## §5. Acceptance Criteria

This workstream is complete only when all conditions hold:

1. Python dependency scan exists and is documented.
2. Container image scan exists and is documented.
3. `config/manifest.yml` version bumps have a defined security / compatibility checklist.
4. There is a published compatibility matrix with supported-state semantics.
5. There is a waiver mechanism with owner + expiry, not free-text excuses.
6. CI enforces at least one security scan gate beyond `detect-secrets`.

---

## §6. Recommended Execution Order

1. **WU-1** Version Truth & Release Freeze Model
2. **WU-4** Semaphore Upstream Security Policy
3. **WU-2** Vulnerability Scanning Gates
4. **WU-3** Compatibility Matrix & Upgrade Verification
5. **WU-5** Waiver, Cadence, and Audit Closure Rules

Reason:
- version truth must be settled before scanners produce meaningful results
- Semaphore is the highest-risk external control-plane dependency in this repo
- waivers should be defined after the real scan noise profile is known

---

## §7. Non-Goals

This plan does **not** mean:
- zero CVEs forever
- blocking every merge on every low-severity finding
- pinning every local dev surface so tightly that contributor setup becomes brittle
- replacing functional tests with scanners

The objective is a **defensible merge / release posture**, not maximal scanner theater.

---

## §8. First Implementation Cut (Recommended)

If this workstream starts in a future branch, the smallest useful first slice is:

1. add the governance docs for version truth + Semaphore upgrade policy
2. add one Python vulnerability scanner
3. add one image vulnerability scanner
4. add a minimal waiver file format
5. wire those into CI as non-optional gates for at least `High` / `Critical`

That is the minimum point where the repo can start answering "is this stack currently carrying known serious vulnerabilities?" with evidence instead of assumption.
