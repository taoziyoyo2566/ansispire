## 1. Purpose / Scope / Out-of-scope / Judgment Criteria

### 1.1 Purpose
为后续阶段（角色移植、ACL 控制面、监控/审计移植、Molecule 验证）奠定 **可信的数据基线**：
- 用户文件是真 YAML 而不是 JSON-in-`.yml`。
- 用户私钥任何时候都不以明文落到 git。
- CLI 操作集对齐上游能力（add/update/delete/list），且默认引导用户走 Vault 加密路径。

### 1.2 Scope（阶段 1 内）
1. 用户数据模型定义（schema + 文件位置 + 命名规则 + 字段加密策略）。
2. Vault 集成策略（encrypt_string per-field vs 全文件 encrypt）。
3. CLI 工具的设计与实现（落地代码归属决策见 §3.4）。
4. 现有 Ansispire 资源的接入点说明（不实际改动它们）：`config/manifest.yml`、`inventory/local/vault.yml`、`.vault_pass`。
5. 安全清算行动项（依赖 IVG §6.2 阶段 0 决策）。

### 1.3 Out-of-scope（阶段 1 不做）
- 角色 `reality_single` / `reality_multi` 的 Ansispire 化（阶段 3）。
- ACL 矩阵（`acl_matrix`）落地到 Ansispire 的 inventory 结构（阶段 2）。
- 监控/审计/订阅 Gist（阶段 4）。
- Molecule 验证（阶段 5）。
- 任何对上游 reality-ops repo 的修改（迁移目标在 Ansispire 这边）。

### 1.4 Judgment Criteria（阶段 1 验收）
- ✅ 任何 `users/<name>.yml` 用 `cat` 直读看不到 X25519 私钥明文。
- ✅ Ansible 在 deploy playbook 里通过 `lookup('file', ...) | from_yaml` 能正确拿到解密后的 `private_key`。
  - 验证命令：`ansible localhost -m debug -a "msg={{ lookup('file', 'runtime/state/reality_users/<sample>.yml') | from_yaml }}"`
- ✅ CLI 至少支持 `add / update / delete / list` 四个动作，行为对照上游 `generate_user.py`（不引入额外依赖路径）。
- ✅ 没有 JSON 内容写到 `.yml` 文件里（`yamllint -d relaxed` 通过）。
- ✅ 用户文件目录、Vault 路径、`.vault_pass` 使用统一变量；CLI 不在源代码里硬编码绝对路径。
- ✅ **CLI `list / update / delete` 在无 vault 密码环境下仍能正常工作**（即 `rm -f .vault_pass && unset ANSIBLE_VAULT_PASSWORD_FILE` 后这三条命令不抛异常）。仅 `add` 需要 vault 密码。详见 §3.3a `_VaultedString` 设计。

## 3. 设计决策（Decisions）

### 3.1 用户文件位置与命名

**决策**: `runtime/state/reality_users/<name>.yml`（推荐）。

理由：
- `inventory/` 在 Ansispire 是 per-env 结构（dev/stag/prod），用户数据是跨环境共享的，硬塞 `inventory/targets/users/` 与现有约定冲突（这正是 Gemini 落地路径的问题）。
- `runtime/state/` 已有先例（`vps_manager` 用 `runtime/state/vps_inventory.yml`）。
- 同时方便被 gitignore 选择性排除——见 §3.2。

**备选**: `data/reality/users/<name>.yml`（新目录），更符合"data plane SSOT"语义；但增加目录层级且需要更新 `.gitignore` / 部署引用。

**Open Decision D1**：路径定为 `runtime/state/reality_users/` 还是 `data/reality/users/`？默认走前者除非用户偏好后者。

### 3.2 Git 入库策略

**决策**: 用户文件**入 git**（加密后），`.vault_pass` 已 gitignore。

理由：
- 用户清单是控制面 SSOT，需要可审计、可回滚、可多人协作 —— 必须入 git。
- 私钥用 `encrypt_string` 包裹后，`cat` 看不到明文，git diff 显示密文，已满足审计需求。
- `.gitignore` 仅需保护 `.vault_pass`（已存在）。

### 3.3a UserStore 抽象（应对未来 DB 迁移）

User 在 D1 反馈中指出长期方向是把用户从文件搬到数据库。阶段 1 实现要预留这条路径，同时通过**复用 Ansible 自带的 `AnsibleLoader`**（D6 决策）解决「私钥被加密时 list/update 怎么读其他字段」的问题（见 review-2026-05-15-gemini-r1 §1.9 + claude 第二轮自检）：

```python
# plugins/reality_manager/reality_manager.py（草案）
import io, shutil, subprocess, sys
from typing import Protocol, Iterable
from ansible.parsing.yaml.loader import AnsibleLoader
from ansible.parsing.yaml.objects import AnsibleVaultEncryptedUnicode
from ansible.parsing.vault import EncryptedString  # !vault | ... 解析后的对象类型

# 复用 Ansible 自带类型作为"密文哨兵"——load 不解密、不抛异常；
# **footgun 警告**：对 EncryptedString 调 str() 会触发解密尝试 → 没 VaultSecretsContext
# 时报 ReferenceError。因此 CLI 任何代码路径下都不许 stringify private_key 字段。


class UserStore(Protocol):
    def get(self, name: str) -> "User | None": ...
    def put(self, user: "User") -> None: ...
    def delete(self, name: str) -> None: ...
    def list(self) -> Iterable["User"]: ...
    def existing_ports(self) -> set[int]: ...


class YamlVaultStore:
    """阶段 1 实现：runtime/state/reality_users/<name>.yml + ansible-vault encrypt_string

    读：复用 AnsibleLoader——不解密 private_key、与 deploy.yml 的 from_yaml 同一路径。
    写：调 ansible-vault encrypt_string CLI（subprocess），把产出的 !vault | ... 块原文写入文件。
    """

    def __init__(self, users_dir: str, vault_password_file: str = ".vault_pass"):
        self.users_dir = users_dir
        self.vault_password_file = vault_password_file
        # 构造时 best-effort 检测；写 vault 字符串前才硬性 require（Gemini r1 finding 2.1 采纳）
        self._vault_cli_available = shutil.which("ansible-vault") is not None

    def _require_vault_cli(self):
        if not self._vault_cli_available:
            sys.stderr.write(
                "未找到 ansible-vault 可执行文件。\n"
                "  - 确认已激活 .venv 并安装 ansible（pip install -r requirements.txt）\n"
                "  - 或在系统层安装：apt install ansible-core / pipx install ansible-core\n"
            )
            sys.exit(2)

    def _load(self, path: str) -> dict:
        with open(path, "r", encoding="utf-8") as f:
            return AnsibleLoader(f).get_single_data()

    def encrypt_field(self, plaintext: str) -> str:
        """调 ansible-vault encrypt_string，返回 !vault | ... 块（含换行的多行字符串）。"""
        self._require_vault_cli()
        # 关键：必须显式 --encrypt-vault-id default
        # 否则 ansible.cfg 已配置 vault_password_file 时 CLI 会报：
        #   "vault-ids default,default are available to encrypt. Specify the vault-id to encrypt with --encrypt-vault-id"
        # 实测命令（IVG-DEEP-AUDIT B1）：
        # echo "$plaintext" | ansible-vault encrypt_string \
        #     --encrypt-vault-id default \
        #     --vault-password-file .vault_pass \
        #     --stdin-name private_key
        # 用 --stdin-name 而不是位置参数：避免 plaintext 出现在 ps aux 输出里
        ...


# 未来：class DatabaseStore: ... 替换 backend 不动 CLI / schema
```

设计要点：
- `cli.py` 只持有 `UserStore` 接口，不直接 import `yaml` / `ansible.parsing.*` / 文件 IO。换 backend 改造面仅限 `reality_manager.py`。
- **D6 决策**：用 Ansible 自带的 `AnsibleLoader`，而不是自写 `_VaultedString`——`!vault | ...` 自动变 `EncryptedString` 哨兵，不解密就保留密文。`list / update / delete` 读到 private_key 拿到的是密文对象——**无 vault 密码也能跑**。
- **Footgun**：`EncryptedString.__str__` 会触发解密尝试。CLI 中必须**遵守纪律**：调试日志、错误消息、序列化输出都不能 `str(private_key)` 或 `f"{private_key}"`。T1.5 测试集必须包含一条「list 命令在 unset VaultSecretsContext 下不抛异常」。
- 写回时调 `ansible-vault encrypt_string --stdin-name private_key`（用 stdin 而非位置参数，避免 plaintext 进 `ps aux`）；产物是带 `!vault |` 头的多行字符串，原文写入 YAML 文件，**不**走 yaml.dump 二次序列化——避免破坏 Ansible 的 vault 标签格式。
- `ansible-vault` 可用性探测：构造时 best-effort，写时硬性 require——保持 list/update 在无 vault 环境可用（§1.4 验收点）。

### 3.3 Schema 与字段加密策略

**决策 schema**（真 YAML，注释友好）:

```yaml
# runtime/state/reality_users/alice.yml
name: alice
uuid: 3eca4074-7908-4622-8933-c0033ad45805
port: 42237
short_id: 17d4a900d6f762b2
public_key: YnX30UUrPRZR04Z2GPkHfE5oaSHPmWmz5uSF-quIeRY
private_key: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  3036323362633562653...（encrypt_string 产物）
groups:
  - basic
hosts:
  - server1
# 兼容字段（缺失 = legacy_all 行为，对齐上游）
# acl_mode: explicit | legacy_all
```

理由：
- `private_key` 是仅有的高敏字段；`public_key`、`short_id`、`uuid`、`port` 都可公开（订阅 URL 里本来就有 uuid/public_key）。
- 选 per-field `encrypt_string` 而非全文件加密的关键理由：**Ansible 的 `lookup('file', ...) | from_yaml` 在文件级 vault 加密时无法解析非 vault 字段做 ACL 过滤**。控制面 pre_tasks 需要在不解密 private_key 的情况下读 `groups/hosts`——per-field 加密是唯一选项。

**Open Decision D2**：是否同时加密 `uuid`？上游不加密；但 uuid 出现在订阅 URL 里，泄露不增加攻击面，建议不加密以保持 deploy.yml 调试便利。**默认不加密**。

### 3.4 CLI 工具归属

**决策**: 实现为 `plugins/reality_manager/`，复用 `vps_manager` 范式。

理由：
- 上游 `generate_user.py` 709 行单脚本 + `--docker` 自举逻辑——是面向单机操作员的工具脚本。
- Ansispire 已经把这类「带子命令 + 调用 playbook + 持久化 runtime state」的工具规范成 plugin（见 `plugins/vps_manager/{plugin.yaml, cli.py, <name>.py, playbooks/, schema.json}`）。
- 走 plugin 范式 = 自动获得 schema 验证、playbook 调度、runtime state 管理、操作日志（runtime/logs/）。
- 阶段 1 暂不实现 `playbooks/`（无远端调用），只实现 `cli.py` + `reality_manager.py` + `schema.json` + `plugin.yaml`；阶段 3 角色移植时再补 playbooks。
- **解耦约束**（Gemini r1 finding 2.5 采纳）：`reality_manager` 仅借用 `vps_manager` 的**目录结构 + plugin.yaml schema + cli 分发模式**，**不 import `plugins.vps_manager` 任何模块**。两个插件平级，不允许跨插件代码依赖。

**Open Decision D3**：plugin 名称 `reality_manager` 还是 `reality_users`？前者更宽（未来可承接节点级操作），后者更精确。默认 `reality_manager`。

### 3.5 Vault 密码源

**决策**: 复用 `.vault_pass`（Ansispire 已有约定，`ansible.cfg` 已配置）。

理由：
- 不引入新文件 / 新 ENV 变量。
- CLI 在 `add` 时调 `ansible-vault encrypt_string --vault-password-file .vault_pass`，失败时抛清晰错误（指向 `.vault_pass` 创建说明）。
- 与 `playbooks/vault_demo.yml` 文档化的用法一致。

### 3.6 CLI 子命令集（对齐上游）

最小可用集：
- `add <name> [--port N] [--groups csv] [--hosts csv] [--min-port N] [--max-port N] [--force]`
- `update <name> [--groups csv | --hosts csv]`
- `delete <name>`
- `list [--wide] [--include-legacy]`

#### `add --force` 与 rotate 的语义差异（Gemini r1 finding 2.4 修正）

| 操作 | uuid | port | short_id | private_key | public_key | groups/hosts |
|---|---|---|---|---|---|---|
| `rotate <name>` *（阶段 1 不实现）* | 保留 | 保留 | 保留 | **重生成** | **重生成** | 保留 |
| `add <name> --force` *（阶段 1 实现，对齐上游 generate_user.py）* | **重生成** | **重生成** | **重生成** | **重生成** | **重生成** | 重置为 `--groups / --hosts` 入参 |

**关键**：`add --force` **不是** rotate 的等价物。前者会破坏客户端订阅 URL（uuid 出现在 vless URL 里）。阶段 0 安全清算时若需要轮换上游 29 份明文私钥，**必须单独实现 rotate**，不要用 `--force` 绕路。

不实现的上游能力：
- `--docker` 自举：Ansispire 已有 venv + `cryptography` 依赖管理（`requirements.txt`），不需要容器内重执行。
- `--details / --include-json` 等 list 模式（上游历史遗留，YAML 化后不需要）。
- JSON 数组型用户文件（上游为兼容遗留保留；阶段 1 只接受 dict）。
- `rotate` 子命令（D4 决策；语义见上表）。

**Open Decision D4**：是否要在 CLI 提供 `rotate <name>` 子命令用于密钥轮换？IVG §6.2 阶段 0 安全清算需要轮换 29 个用户，如果未来 Ansispire 也运营 Reality 节点，CLI 内置轮换很自然；但阶段 1 不实现也行（手动 `delete` + `add` 等价）。**默认本阶段不实现，留给阶段 5 之后**。

### 3.7 与 IVG §6.2 阶段 0「安全清算」的关系

**决策**: 阶段 1 **不包含** 已泄露用户密钥的轮换。

理由：
- 阶段 0 是迁移**前提**（决定要不要把上游 29 个用户迁过来 / 用什么密钥迁），属业务/运维决策，不在工程化迁移范围。
- 阶段 1 的 CLI 必须能够支持「干净起步」——`add` 一个全新用户产出合规的加密文件——这就是阶段 1 的验收点。
- 用户决定阶段 0 处理方案后，阶段 1 的 CLI 可以无缝接入。

## 7.6 Future Migration Path: YAML/Vault → Application DB + HashiCorp Vault

> 触发：user 2026-05-16 问「用户资料最终通过数据库管理是否符合 ansible 最佳实践」。调查结论：✅ 符合，且**业务数据（reality 用户）与基础设施数据（vps 节点）应分开**。本 plan §3.3a D1 已经预留 UserStore Protocol 抽象，本节明确演进路径。

### 7.6.1 关键 separation（与 vps-manager-v2 plan §7.5 协同）

| 数据类型 | 归属 | 当前 backend | 长期 backend |
|---|---|---|---|
| **业务数据**：reality 用户的 X25519 私钥 / UUID / port / short_id / ACL groups+hosts / 订阅元数据 | reality_manager 应用层 | `runtime/state/reality_users/<name>.yml` + ansible-vault encrypt_string | **应用 DB**（PostgreSQL / SQLite）+ **HashiCorp Vault** 管私钥（动态 secrets + rotation） |
| **基础设施数据**：VPS 节点 host/port/ssh_key/group | vps_runner / Ansible inventory | `inventory/<env>/hosts.yml` + `host_vars/<alias>.yml` | NetBox / 自建 CMDB + dynamic inventory plugin（见 vps-manager-v2 §7.5）|

**反 pattern**：业务用户数据塞 Ansible inventory（破坏关注点分离）；基础设施节点塞业务 DB（混淆 SSOT）。

### 7.6.2 演进路径（reference，不在本 plan 实施范围）

| 阶段 | reality_users backend | private_key 管理 | 触发条件 |
|---|---|---|---|
| 现在（本 plan 阶段 1） | YamlVaultStore（YAML + ansible-vault encrypt_string） | per-field encrypt_string | dev 阶段，用户数 < 100 |
| 中期 | `DatabaseStore` 实现 UserStore 接口（SQLite/PostgreSQL）；private_key 字段仍走 vault encrypt_string | 同左 | 用户数 > 100 或需要多 operator 并发写 / 业务 UI 接入 |
| 长期 | DatabaseStore + HashiCorp Vault transit engine | 私钥不入 DB，DB 只存 vault reference path；运行时通过 HCV API 获取 | production：需要 secret rotation + audit log + 细粒度 ACL |

### 7.6.3 切换成本评估（为什么 plan §3.3a UserStore 抽象重要）

阶段 1 plan §3.3a 草案约束：
- `cli.py` 只持有 `UserStore` 接口，不直接 import `yaml` / `ansible.parsing.*` / 文件 IO
- 换 backend 改造面**仅限** `reality_manager.py` 中 `YamlVaultStore` → `DatabaseStore` 替换

切换到 DB 时：
- ✅ 不动 `cli.py`（用户操作 CLI 体验零变化）
- ✅ 不动 `schema.json`（数据 schema 跨 backend 一致）
- ✅ 不动 deploy.yml playbook（playbook 通过 reality_manager 拿到的 dict 不知道也不关心 backend）
- 🔄 改 `reality_manager.py`：新增 `class DatabaseStore`，并把 backend 选择推到环境变量或配置
- 🔄 数据迁移脚本：`yamlvault_to_db.py`（一次性）

### 7.6.4 演进决策原则

- **业务数据归应用 DB；基础设施归 NetBox**——两者**不混用同一个 DB**，除非明确 trade-off（dev 简化场景）
- **Secrets 演进 Ansible Vault → HashiCorp Vault**：HCV 支持 dynamic secrets / rotation / fine-grained ACL，是 production secrets management 标准
- **DB 引入前置条件**：业务 UI 接入需求出现 / 用户数突破 100 / 多 operator 并发写 — 三者任一触发再启动 DB migration plan
- 切换时配套：HashiCorp Vault 部署 + 数据迁移脚本 + 备份/恢复 runbook + audit log 接入 Ansispire Audit Plane

### 7.6.5 为什么现在不做

- **W-R14 / [[dev-stage-pragmatism]]**：dev 阶段引入 DB + HCV 是过度工程
- 用户数 < 100，YAML + ansible-vault 完全够（且 git diff 可审计）
- UserStore 抽象已经在了（plan §3.3a），未来切换改动可控
- HCV 是独立服务，需要运维成本——production 上线后再做
