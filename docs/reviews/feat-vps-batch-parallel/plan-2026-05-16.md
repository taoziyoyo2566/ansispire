## 1. Purpose / Scope / Out-of-scope / Judgment Criteria

### 1.1 Purpose

把 vps_manager 从「per-task 起一个 ansible-playbook 进程」的串行模式，升级为「同 action 聚合到单进程 + Ansible forks 并发」的批量模式，让「同时 onboard 5 台新 VPS」从 N×T 降到 ~T（T = 单节点 onboard 耗时）。

### 1.2 Scope（round 2-3 落地范围）

1. `vps_manager.py::process_paths` 增 batching 分支（按 action 切片）。
2. 新增 `build_batch_ansible_inventory(tasks)` —— 把 N 个 task 合并到一份 inventory，task 私有数据进 `host_vars`。
3. 新增 `callback_plugins/vps_batch_reporter.py` —— 收集 per-host `runner_on_ok / on_failed / on_unreachable`，落地到 `runtime/state/tasks/<batch_id>/results.yml`。
4. `update_inventory_after_success` 改为接受 `list[task]` 顺序回写（消除并发写 vps_inventory.yml 的可能）。
5. 端到端测试 `tests/test_batch_processing.py`（单元 + 集成）。
6. 1 个 Molecule scenario 验证多节点 onboard 同时落地。

### 1.3 Out-of-scope（本 plan 不做）

- **跨 action 混合 batching**（onboard + modify 同批跑）：暴露 dependency 顺序问题，留 backlog。
- **进程内多线程包装**：违反 IVG §6 经验教训。
- **重写 playbook**：onboard.yml/modify.yml/audit.yml 内部逻辑不动。
- **reality_manager**：feat-reality-migration plan 阶段 1 完成后再回头看是否复用本 batching 模型（默认结论：不复用，reality 是同步 CLI）。
- **callbacks 全局 enable**：不动 `ansible.cfg` 的 `callbacks_enabled`，batch reporter 仅在 batching code path 用 env 注入。

### 1.4 Judgment Criteria（验收门槛）

- ✅ inbox 含 3 个 onboard task → 单次 `ansible-playbook` 调用，3 host 并发 SSH，总耗时 ≈ max(单节点)，而非 sum(三个节点)。
- ✅ 其中 1 个节点 SSH 失败 → 该节点标 failed、其他 2 个仍走 success archive 流程；vps_inventory.yml 只新增 2 条记录。
- ✅ `runtime/state/tasks/<batch_id>/results.yml` 含 per-host status + per-host 错误消息。
- ✅ 旧的单 task 路径仍可用：`vps-manager process` inbox 只 1 个 task 时不走 batching 分支（fallback 到现有 `process_file`），行为零回归。
- ✅ `make test-vps-manager` 全绿；CI `python-tests` 跑同一 target（B3 修复同步生效）。
- ✅ Molecule scenario `batch_onboard`（3 个容器节点）跑 PLAY RECAP 显示 3 host ok=N 同步。

## 3. 设计决策（Decisions）

### 3.1 批量粒度：同 action 聚合，不跨 action 混合

```python
# vps_manager.py（草案，仅示意结构）
def group_pending_by_action(self, pending_paths: list[Path]) -> dict[str, list[tuple[Path, dict]]]:
    """读 + normalize 后按 action 切片；保留 path 用于后续 archive。"""
    groups: dict[str, list[tuple[Path, dict]]] = {}
    for path in pending_paths:
        task = self.normalize_task(read_yaml(path))
        groups.setdefault(task["action"], []).append((path, task))
    return groups

def process_paths(self, pending_paths: list[Path]) -> ProcessSummary:
    # ... preflight unchanged ...
    groups = self.group_pending_by_action(pending_paths)
    summary = ProcessSummary(processed=0, failed=0, blocked=0, issues=[])
    for action, items in groups.items():
        if action in BATCHABLE_ACTIONS and len(items) > 1:
            summary = merge(summary, self.process_batch(action, items))
        else:
            for path, _ in items:
                summary = merge(summary, self._wrap_process_file(path))
    return summary
```

**理由**：
- 不同 action 用不同 playbook（PLAYBOOK_BY_ACTION 表），混合 batching 需多 playbook orchestration → 复杂度跃迁。
- 同 action 单 playbook 是 Ansible 原生强项，零额外抽象。
- inbox 实际场景几乎都是同 action 批量（一次 onboard 5 台新 VPS、一次 audit 所有节点）。

### 3.2 并发引擎：Ansible 原生 forks

- 不自写 Python `ThreadPoolExecutor` / `asyncio` 包装（IVG §6 经验教训：「优先 Ansible 原生扩展」）。
- 在 batch 执行时显式 `--forks N`（`N = min(len(tasks), ANSIBLE_FORKS_MAX)`，默认 max=10）。
- ANSIBLE_FORKS_MAX 通过 `config/manifest.yml::ansispire_versions` 或独立 key 注入——见 D2。

### 3.3 Callback Reporter

```python
# callback_plugins/vps_batch_reporter.py（草案，仅示意）
from ansible.plugins.callback import CallbackBase

class CallbackModule(CallbackBase):
    CALLBACK_VERSION = 2.0
    CALLBACK_TYPE = 'aggregate'
    CALLBACK_NAME = 'vps_batch_reporter'

    def __init__(self):

        self.results = {}  # alias -> {status, msg, last_task}
        self.output_path = os.environ.get('VPS_BATCH_RESULTS_PATH')

    def v2_runner_on_ok(self, result):
        self._record(result, status='ok')
    def v2_runner_on_failed(self, result, ignore_errors=False):
        self._record(result, status='failed', msg=str(result._result))
    def v2_runner_on_unreachable(self, result):
        self._record(result, status='unreachable', msg=str(result._result))

    def v2_playbook_on_stats(self, stats):
        # write self.results -> self.output_path (YAML)
        ...
```

- **注入方式**：batch 执行时 env 注入 `ANSIBLE_CALLBACKS_ENABLED=timer,profile_tasks,vps_batch_reporter` 和 `VPS_BATCH_RESULTS_PATH=runtime/state/tasks/<batch_id>/results.yml`。**不动** `ansible.cfg`。
- 单 task 路径**不**启用该 callback——避免干扰 `human_log.py` 现有行为。
- `results.yml` 后被 `archive_batch_success` 切分为 per-task archive（保持「一个 task 一份 archive」的现有契约）。

### 3.4 Inventory 顺序回写（不引入文件锁）

```python
def update_inventory_after_batch(self, results: dict, tasks_by_alias: dict[str, dict]) -> None:
    inventory = self.load_inventory()  # 单次读
    touched_paths: set[str] = set()
    for alias, result in results.items():
        if result["status"] != "ok":
            continue
        touched_paths |= self.update_inventory_after_success(
            tasks_by_alias[alias], result["task_id"], inventory
        )
    self.save_inventory(inventory)  # 单次写
    if touched_paths:
        self.sync_ssh_configs(self.load_inventory(), touched_paths)
```

- Ansible 子进程跑完 → 主进程顺序处理 results → 一次 read-modify-write。
- 不需要 `fcntl.flock` / `threading.Lock`——主进程在 batch 执行期间不会触碰 vps_inventory.yml。
- 失败 host：跳过 inventory 更新，但仍走 `archive_failure` 路径。

### 3.5 错误隔离与 archive 分类

- batch 单进程 returncode 不再是「整批 pass/fail」的判据——必须读 `results.yml` 才能分类。
- per-task archive 路径不变（`runtime/archive/vps/{success,failure}/<task_id>/...`）。
- batch_id（`vps-batch-<timestamp>-<action>`）作为 cross-reference 写入每个 archive 的 `meta.yml`，方便定位「这条 task 是哪批跑的」。

### 3.6 单 task fallback（零回归保证）

```python
BATCHABLE_ACTIONS = {"onboard", "recover"}  # 首批；audit 已天然支持多 alias，但 inventory 形态不同，留 D3 决策
# audit 走自己的 multi-alias 路径（既有 target_aliases 机制）
# modify/docker_host/deploy_compose: 默认走单 task 路径
```

- inbox 只 1 个 task → 强制走旧 `process_file`，行为完全等价。
- 即使 action 在 BATCHABLE_ACTIONS 内，单 task 也不进 batching——避免引入「为了 1 个 host 跑 callback」的开销。
