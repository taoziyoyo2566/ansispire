# Round 13 — first-time onboard clears stale SSH host keys

**Date:** 2026-05-24
**Branch:** `feat/vps-manager-v2`
**Level:** 🟡 [L1] Engineering (bug fix; touches SSH connection semantics)
**Reference:** no standalone plan doc — single-cause fix surfaced from a live onboard failure (`make vps-add-host` → `hk-alm9` → `REMOTE HOST IDENTIFICATION HAS CHANGED!`). Direction confirmed with user via AskUserQuestion: "清旧 key 再重新 pin".

## Problem

Onboarding `hk-alm9` (82.152.164.144) failed at the first bootstrap task:

```
REMOTE HOST IDENTIFICATION HAS CHANGED!
...
Password authentication is disabled to avoid man-in-the-middle attacks.
root@82.152.164.144: Permission denied (...).
```

Root cause: the IP had 3 stale host keys in the operator's `~/.ssh/known_hosts` (prior tenant / OS reinstall). The new VPS presents a different ED25519 key. `ansible.cfg:34` sets `StrictHostKeyChecking=no`, but that only auto-accepts **unknown** hosts — on a **changed** key OpenSSH hard-fails and disables password / keyboard-interactive auth. The onboard tool considered fresh-unknown hosts (TOFU) but not IP-reuse / reinstall, which is a high-frequency case for VPS onboarding.

## Best-practice pre-check (W-R18)

Ansible's `ansible.builtin.known_hosts` module manages entries as a task, which requires an established connection — it cannot solve a *pre-connection* host-key conflict. Industry onboarding tools clear the conflicting entry on the control node before connecting (`ssh-keygen -R`). The plugin already does connection-time probing in Python (`ssh_probe`), so the purge belongs in the same layer. **Conclusion: direction matches** — clear-and-re-pin in Python control-side.

## Intent

Preserve TOFU/MITM protection (we still pin the host key going forward) while unblocking the dominant IP-reuse / reinstall case: purge the conflicting entry immediately before the bootstrap connection so SSH re-pins the new key. Purge is scoped to first-time onboard only (managed-repair mode is untouched — a working managed channel has no stale-key issue).

## Second issue (same run): fail2ban fails on RHEL family

After the host-key fix let onboard connect, the live run against `hk-alm9` (AlmaLinux 9) reached `Install fail2ban support packages` and failed: `No package fail2ban available`. The play had already taken every RedHat branch (dnf Docker repo tooling, SELinux cgroup boolean).

Root cause: fail2ban ships in **EPEL**, not RHEL/AlmaLinux/Rocky base repos; `onboard.yml` (standalone, does not use `roles/common`) never enabled EPEL. `roles/common` works because it seeds `epel-release` via `_common__os_packages` before its fail2ban task — the established project pattern (W-R18 alignment).

Fix: (a) new `Enable EPEL for fail2ban (RedHat family)` task (`ansible.builtin.dnf: epel-release`, gated on `os_family == RedHat` + fail2ban enabled) before the install; (b) `python3-systemd` install condition changed from Debian-specific to `service_mgr == systemd` (the jail template uses `backend = systemd` on any systemd host, so RHEL needs it too — same package name on both families).

Self-check: syntax-check passed; `ansible-lint` 0 failures / 0 warnings (production profile); Jinja eval confirms `['fail2ban', 'python3-systemd']` for systemd hosts. Gate 3 (live RHEL onboard) is the operator's next wizard run — it needs the interactive SSH password.

## Third issue (same run): unresolvable IP/hostname accepted by wizard

Re-run derailed by operator input: `IP / hostname` got `hk-alm9` (the alias) while `User` got `82.152.164.144` (the IP, correctly rejected by `_validate_ssh_user`). `ansible_host` became `hk-alm9` → `Could not resolve hostname hk-alm9` ~3 tasks in. Root cause is the typo, but the wizard's `_validate_hostname` only checks charset/length — `hk-alm9` is a syntactically valid hostname, so it passed.

Fix: new `core.host_resolves(host)` (`socket.getaddrinfo`, True for IP literals and DNS/`/etc/hosts`-resolvable names). Wizard IP prompt now warns + re-prompts when it doesn't resolve, with an explicit `y` override for hosts not yet in DNS. Fails fast at the prompt instead of mid-play. Verified against the incident's real values: `host_resolves('hk-alm9')` → False (rejected), `host_resolves('82.152.164.144')` → True (passes). No wizard-test regression — existing tests use IP literals, which always resolve.

Both are conditional on the host's actual SELinux mode / firewalld state. Fixing them is a distinct RHEL-onboard-completion effort (mirror UFW logic for firewalld + add SELinux port labeling), pending a scope decision with the user.
