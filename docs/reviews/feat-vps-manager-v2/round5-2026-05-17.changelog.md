## 2. Intent per change (grouped by review finding)

### 2.1 P1.1 — SSH config reversibility + handler-based reload (R5.1 + R5.2)

Review said onboard.yml mutates `/etc/ssh/sshd_config` (comment-out via `replace`) and remove.yml doesn't reverse it; also that drop-in removal didn't trigger sshd reload. Both gaps closed:

- **Handler model**: 8× inline `systemd state=reloaded/restarted` tasks replaced with `notify:` → `Reload sshd` / `Reload systemd manager` / `Restart sshd.socket` handlers, with `meta: flush_handlers` placed AFTER each `sshd -t` validation so reload only fires when config is provably good. This matches the Ansible native change-driven reload idiom.
- **Sentinel marker**: `# ANSISPIRE-COMMENTED: <directive> <value>` preserves the original value (the prior `# <directive> managed by /etc/ssh/...` template threw the value away — data loss made true revert impossible). `remove.yml` runs the reverse `replace` when `--cleanup-remote` is passed.
- **Backward-compat caveat**: hosts onboarded BEFORE Round 5 used the old marker; `--cleanup-remote` won't auto-revert those (operator note in remove.yml task comment). Acceptable: vps_runner has only been used on dev VPS so far, all of which can be re-onboarded.

### 2.2 P1.2 — Docker scope deferred (3 sites in sync)

`features.docker: true` was set in every host_var but no playbook actually installed/configured Docker — Ansible's worst pattern ("variable exists, no execution semantic"). Either ship the implementation or remove the variable; chose remove (review's suggested option a) because: (a) deferring respects [[dev-stage-pragmatism]] — Docker is a future capability, not a current commit; (b) the cutover deliberately deferred `docker_host`/`deploy_compose` parity. Updated host_vars + group_vars + operations.md + feature-map + deleted unused template — single coherent removal across the codebase.

### 2.3 P1.3 — Artifact env scrubbing (envvars whitelist + scrubbed_environ ctx)

Review pointed out `suppress_env_files=True` only blocks the `env/` file from being written, but the artifact's `command` file still records the runner subprocess's full env dict. If a caller had `OPENAI_API_KEY` etc. in their env, it'd land in the artifact. Two-layer fix:
- `_build_runner_envvars()` constructs the minimal envvars: PATH (venv bin first, then system paths), ANSIBLE_CONFIG / ANSIBLE_COLLECTIONS_PATH / ANSIBLE_ROLES_PATH, plus a 5-key locale allowlist (HOME/LANG/LC_ALL/LC_CTYPE/TERM). Anything not on the allowlist never reaches ansible-runner.
- `_scrubbed_environ()` ctx manager temporarily replaces `os.environ` with the allowlist for the duration of the `ansible_runner.run()` call, because ansible-runner inherits os.environ as the *floor* for the subprocess env. Without the ctx scrub, the allowlist would only overlay (not replace) the ambient env.
- New integration test `test_integration_envvars_artifact_excludes_unwhitelisted` injects a canary token `FAKE_LEAKED_TOKEN_DO_NOT_USE=sk_leak_canary_value_12345` and asserts it's absent from `runtime/logs/.../command` after a real ansible-runner invocation against TEST-NET-1. Regression guard.

Docstring updated to clarify: `suppress_env_files=True` is necessary but not sufficient; the envvars allowlist is the real boundary.

### 2.4 P1.4 — Direct CLI is now self-sufficient (PATH includes venv bin)

Review showed `.venv/bin/pytest plugins/vps_runner/tests/ -m integration` failed with rc=127 ("ansible-playbook not found") because the runner's env didn't include venv bin, so it only worked via `make` which exports PATH. Fix bundled with R5.3 (same `_build_runner_envvars` change): `PATH` now starts with `Path(sys.prefix) / "bin"` so ansible-playbook resolves regardless of caller's PATH. New integration test `test_integration_run_playbook_without_path` strips venv bin from PATH and asserts rc≠127 — regression guard for the Makefile-independence claim.

### 2.5 P2 — group_vars extraction (already done in WIP, verified)

Review: shared defaults sprinkled across 4 host_vars (security policy, feature toggles, key paths) → drift risk. Moved to `inventory/vps_runner/dev/group_vars/vps_targets.yml`. The onboard.yml combine pattern `vr = vps_runner_defaults | combine(vps_runner)` is necessary because Ansible's default `hash_behaviour=replace` doesn't merge dict keys between group_vars and host_vars automatically — documented in the new file's header.

### 2.6 P2 — Native Ansible SSH validation (R5.3)

Review: `delegate_to: localhost` + raw `ssh -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null` bypasses inventory's connection model, blanket-disables host key check, and requires local OpenSSH CLI + key path. Replaced with native pattern: `meta: reset_connection` → `wait_for_connection` (with per-task `vars:` for new port/user/key) → `command` over the new connection. Two sites covered (after transitional sshd reload + after final lockdown). The `wait_for` TCP port probe at line ~475 stays (it's a smoke test, not a connection-model bypass).

Inventory's `ansible_ssh_common_args` / ProxyJump / ControlPersist all respected. The host key check now follows whatever the inventory's `ssh_args` config sets (operator can set `StrictHostKeyChecking=accept-new` for first-onboard).

### 2.7 W-R18 framework best-practice pre-check (recorded in plan §0.2)

All 3 R5.x fixes use native Ansible patterns with in-repo precedents:
- `handlers:` + `notify:` + `meta: flush_handlers` — Ansible standard
- `meta: reset_connection` + `wait_for_connection` — `roles/geerlingguy.docker/tasks/docker-users.yml:10`
- Sentinel-based reversible `replace` — chose this over `blockinfile` (project precedent in `roles/webserver/tasks/configure.yml:42`) because it preserves the original directive value verbatim (smallest correct diff)

No reinvention; direction verified against project usage before implementing.
