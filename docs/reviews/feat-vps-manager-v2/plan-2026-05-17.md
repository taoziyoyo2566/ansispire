For the reversibility item, two native-conforming alternatives:
- **(a) sentinel-prefixed `replace`** — onboard substitutes `<directive> <value>` → `# ANSISPIRE-COMMENTED: <directive> <value>`. remove.yml's reverse: `^# ANSISPIRE-COMMENTED: (.*)$` → `\1`. **Pro**: minimal diff vs current code; preserves the original value verbatim (no data loss). **Con**: still uses `replace`, not the more native `blockinfile`.
- **(b) full `blockinfile` rewrite** — onboard saves originals, manages a marked block instead. **Pro**: idiomatic. **Con**: larger diff; touches a working hardening path the user already validated on hk-d12 / hk-d13 / hk-u24 via 22-test parity; high regression cost for the same outcome.

Decision: **(a)**. Smallest correct change that closes the symmetry gap. Recorded in §3 R5.2.

Sources consulted: WebSearch was not needed — both patterns are documented in Ansible builtin docs and already present in-repo. The decision is precedent-driven.

## §3 Decision rationale per change

### R5.1 — Add `handlers:` block to onboard.yml

**Decision**: append a `handlers:` section after the play's `tasks:` block with 3 handlers:
- `reload sshd` → `ansible.builtin.systemd: name={{ vps_ssh_service_name }} state=reloaded` (skip in check mode)
- `reload systemd manager` → `ansible.builtin.systemd: daemon_reload=true` (skip in check mode)
- `restart sshd.socket` → `ansible.builtin.systemd: name={{ vps_ssh_socket_unit_name }} state=restarted` (skip in check mode AND skip when `vps_ssh_socket_activation_enabled=false`)

**Rationale**: WIP introduced `notify:` calls but the corresponding handlers block was never added. Ansible treats undefined handlers as a warning (not fatal), so syntax / lint pass but at runtime the reload never fires → silent regression vs the pre-WIP state. This is exactly what W-R15 gate 3 (functional verification) is supposed to catch.

**Why handlers (not inline `systemd`)**: matches the pre-WIP intent of moving reload semantics to native handler-based change-driven model; reverting to inline systemd would undo the WIP's improvement.

### R5.2 — Reverse-`replace` in remove.yml for SSH reversibility

**Decision (per §0.2 (a))**:
- onboard.yml: change the `replace:` template from `'# \1 managed by /etc/ssh/sshd_config.d/00-ansispire.conf'` to `'# ANSISPIRE-COMMENTED: \1'`. (Old text is still informational but moves to a doc comment if needed; the sentinel `ANSISPIRE-COMMENTED:` is the marker for reverse.)
- remove.yml (when `vps_cleanup_remote=true`): add a task that does the reverse — `replace: regexp='^# ANSISPIRE-COMMENTED: (.*)$' replace='\1' path=/etc/ssh/sshd_config backup=true`. Notify the same `reload sshd` handler. Then validate via `sshd -t` (already present).
- remove.yml: add a `handlers:` block with `reload sshd` (same definition as onboard.yml).
- remove.yml: existing `Remove Ansispire managed sshd drop-in` task should also `notify: reload sshd` (currently it doesn't reload after dropping the drop-in — silent issue parallel to onboard's pre-WIP).

**Rationale**: smallest diff that closes the symmetry gap. The sentinel approach preserves the original directive value verbatim (vs `blockinfile` which would lose the original on first onboard since we'd have to overwrite it). `backup: true` retained as defense-in-depth.

**Caveat noted in changelog**: any host onboarded BEFORE this round had its sshd_config commented with the old `'# \1 managed by ...'` form; `--cleanup-remote` won't auto-revert those. Documented as an operator note (manual `sed -i 's|# \(.*\) managed by .*|\1|' /etc/ssh/sshd_config` if needed). Acceptable because: (a) the only hosts so far onboarded by vps_runner are dev VPS, (b) dev/test paradigm — users can re-onboard from scratch.

### R5.3 — Native Ansible SSH validation, not raw `ssh` from localhost

**Decision**: replace the 2 raw-ssh validation tasks ("Validate managed user sudo on new SSH port" + "Validate final managed login") with:

```yaml
- name: Reset Ansible connection to pick up new SSH port
  ansible.builtin.meta: reset_connection

- name: Re-validate connection using new managed port + user
  ansible.builtin.wait_for_connection:
    timeout: 30
  vars:
    ansible_port: "{{ vps_ssh.managed_port | int }}"
    ansible_user: "{{ vps_managed.user }}"
    ansible_ssh_private_key_file: "{{ vps_managed.ansible_key.private_key }}"

- name: Validate managed user sudo (native)
  ansible.builtin.command: id
  become: true
  changed_when: false
  vars:
    ansible_port: "{{ vps_ssh.managed_port | int }}"
    ansible_user: "{{ vps_managed.user }}"
    ansible_ssh_private_key_file: "{{ vps_managed.ansible_key.private_key }}"
```

(The `wait_for_connection` for the managed_port — the localhost-side `wait_for` port probe that already exists at line 475 stays; it's a TCP-level smoke test, not a connection-model bypass.)

**Rationale per review P2**:
- Respects inventory's `ansible_ssh_common_args` / ProxyJump / ControlPersist
- Doesn't require localhost OpenSSH CLI + local key path (portable to execution environments)
- Doesn't blanket-disable `StrictHostKeyChecking` — the new host's key will land in the operator's `known_hosts` by way of the first successful connection (Ansible's own SSH-via-OpenSSH still applies its `ssh_args` from inventory, which can include `StrictHostKeyChecking=accept-new` if the operator chose that, but that's an inventory decision not a hard-coded `no`)

**Caveat**: `reset_connection` is a known Ansible gotcha — it resets the persistent control socket but the new vars only apply for subsequent tasks. Tested via `--check` first; if behavior differs on a real run, fall back to a second `play:` block with the new connection vars (documented in changelog if used).
