## Why

Onboarding `hk-alm9` (AlmaLinux 9) surfaced the gaps one layer at a time. ## Design decisions

- **Defensive gating** — WU2 only manages firewalld when it is the *active* firewall (skip when absent/stopped → host uses nftables / cloud SG; enabling it could silently drop traffic). WU3 labels the port under enforcing *and* permissive (harmless, future-proof), skips when SELinux disabled. So the code is correct for all RHEL hosts without reading this host's state first.
- **fail-soft scope** — only the optional fail2ban hardening degrades gracefully; core onboarding (Docker, managed user, SSH lockdown, firewall, SELinux port) stays hard-fail. Deferred fail2ban is re-addable via `modify --toggle-fail2ban on` (already supported).
- **firewalld vs UFW asymmetry** — firewalld's default zone is deny-incoming/allow-outgoing by default, so (unlike UFW) no explicit default-policy tasks; only port-opens + boot-enable.

## Live-run iteration — EPEL poisoned all dnf ops

The first WU1 design (install `epel-release` enabled, fail-soft only on the fail2ban task) was incomplete. The live AlmaLinux re-run then **hung 14 min at `Install Docker repository tooling`** — a step that had succeeded in 2.7s the previous run. Cause: the earlier run had installed `epel-release` (enabled); with EPEL unreachable from the host, *every* subsequent dnf op (including Docker's `dnf-plugins-core`) hung refreshing EPEL metadata. fail-soft scoped to the fail2ban task didn't cover the dnf operations that ran *before* it.

Verified the install **method** is correct (EPEL → `dnf install fail2ban` is the official AlmaLinux 9 path; CRB not required — WebSearch). The bug was EPEL repo hygiene. Corrected per dnf best practice: EPEL disabled-by-default + on-demand `enablerepo`, and neutralize a pre-existing enabled EPEL before any dnf op. Application of [[feedback-proactive-failure-audit]]: the failure class is "an unreachable optional repo must never block core dnf ops".

**Second iteration (same host):** with Docker unblocked, the `enablerepo: epel` fail2ban install then hung ~4 min — `dnf.conf` `timeout`/`retries` are *per-connection*, but EPEL's metalink fans out to dozens of mirrors, so the total isn't bounded. Replaced the dnf-level bound with a hard wall-clock cap: `timeout -k 5 30 dnf --enablerepo=epel makecache` probes EPEL (kills the process at 30s, no orphan holding the dnf lock); the fail2ban install is gated on `rc == 0`, else deferred + warn. This guarantees onboard never hangs on EPEL regardless of mirror fan-out.
