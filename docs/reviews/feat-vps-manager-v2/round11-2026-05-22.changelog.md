1. **password flow 经 ansible-runner 必死锁**：cli.py 把 `--ask-pass --ask-become-pass` append 到 cmdline，但 `ansible_runner.run()` 默认不分配 PTY，密码 prompt 既看不到也读不到 stdin。后果：自从 R4-b 切到 ansible-runner，**密码登录路径从未真正能跑通**。

## 2. Intent per change

### 2.1 为什么不沿用 `--ask-pass` 修补，而是改用 `passwords=` dict

ansible-runner `passwords=` 是官方推荐的非交互式密码注入（[ansible-runner docs](https://ansible-runner.readthedocs.io/en/stable/intro.html#ansible-runner-passwords)）。机制：subprocess 把子进程 stdout 流式匹配 regex，命中即把对应密码注入 stdin。**绕过了 ansible-playbook `--ask-pass` 对 PTY 的硬依赖**。密码不进 artifact `command` 文件或 envvars file（W-R18 框架-原生 vs 各种 hack 的取舍）。

### 2.2 为什么把 bootstrap user/port 也纳入 wizard 收集而不是仅 group_vars 默认

操作员实际遇到的 VPS provider 默认行为差异（OpenSSH 默认 22 但某些镜像直接 1156；root 是默认但 Hetzner / 部分 cloud-init 强制创建非 root user）。把这两条字段纳入 wizard 而不是事后让操作员手改 host_vars，是「wizard 一次成功」目标的核心。

### 2.3 临时密钥的项目内 vs `~/.ssh/`

`runtime/keys/vps_runner/<alias>.key` 落地的 3 个原因：

- (a) 不污染 `~/.ssh/`（操作员 SSH 生态边界清晰）
- (b) `runtime/` 已 gitignored，零额外配置
- (c) 项目内位置允许 `_assert_path_in_dir` 复用 R9 containment 校验

成功后清理 + 失败保留 + host_vars `bootstrap_key` 字段串联起完整生命周期：操作员能在 onboard 中断后**不再手敲密码或重粘贴**就直接 `onboard --first-time` 接续。

### 2.4 同名 alias 4 选项菜单 vs R7 简单拒绝

R7 行为：alias 已存在 → 拒绝，让操作员重写一个 alias。R11 实际场景中操作员的需求更细：

- 选项 1 跳过：操作员只是想确认 alias 存在，不动
- 选项 2 改名：操作员认了重名，换个 alias 继续
- 选项 3 验证：操作员怀疑现有配置坏了，需要客观判定
- 选项 4 覆盖：操作员清楚现有配置失效，需要强制重建

选项 3 的「验证」是 **schema → ssh probe → ansible ping** 三步：schema 是结构性，ssh probe 测物理连通，ansible ping 测 mgmt 链路。任何一步失败立即报具体故障点 + 询问是否覆盖。

### 2.5 弃用 `make vps-onboard` 而非保留兼容

它在 ansible-runner 切换后从来没真实跑通过。保留只会误导操作员。`make vps-reonboard` 是新名字代表新语义（key-only 重 onboard），文档变更同步引导操作员。
