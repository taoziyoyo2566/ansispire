## 2. Charset policy — rationale

### 2.1 alias: `^[A-Za-z0-9][A-Za-z0-9_.\-]*$`, ≤63 chars

| Property | Reason |
|---|---|
| **Must start alnum** | No leading dash → can't be confused with a CLI flag downstream (`vps-runner remove --alias -foo` would otherwise be ambiguous). No leading dot → can't accidentally produce a hidden file (`host_vars/.hidden.yml` won't show in `ls`). |
| **Allowed: `_-.`** | Matches the existing fleet's naming (`hy-hk-u24`, `de-d12-1`, `test-r7-wizard`); allows `.` for FQDN-ish aliases. |
| **Rejected: `/`, `\`, whitespace, newline, `#`, `;`, control chars** | Each of `/` and `\` is a path separator (traversal vector); whitespace/newline can inject SSH-config directives or break YAML key parsing; `#` is YAML/SSH comment; `;` is shell separator. |
| **≤63 chars** | Keeps inventory `hosts.yml` keys readable; matches the DNS label limit (so an alias can safely become a hostname-prefix in templates if needed later); bounded length defends against pathological inputs (memory, log-line wrap). |

### 2.2 hostname: `^[^\s#]+$`, ≤253 chars

Accepts IPv4 (`192.0.2.1`), IPv6 (`::1`, `2001:db8::1` — colons OK), DNS (`vps.example.com`). The validator does NOT enforce that the string is a syntactically valid address; that's `onboard.yml`'s `assert` job. R9's contract is narrower: prevent the string from breaking out of the rendered `HostName <value>` SSH-config directive.

Rejected: any whitespace, newline, `#`. These three suffice — see [OpenSSH config grammar](https://man.openbsd.org/ssh_config): tokens are whitespace-separated, comments are `#` to end-of-line, directives are newline-terminated. With those three banned, the rendered line is provably single-directive.

### 2.3 ssh user: `^[A-Za-z_][A-Za-z0-9_-]*$`, ≤32 chars

POSIX recommendation: `[A-Za-z_][A-Za-z0-9_-]*[$]?`. R9 drops the trailing `$` because Ansible's `become_user`/`ansible_user` doesn't use NIS+ user-with-suffix semantics. Length cap 32 mirrors `LOGIN_NAME_MAX` on most Linux distros (defined in `/usr/include/bits/local_lim.h` as 256 on Linux but the de-facto limit for `useradd` is 32). Matches the fleet's actual users (`ansible`, `deploy`).

### 2.4 What's NOT validated by R9

- **port** — already covered by `add_host` arithmetic checks (≠22, 1024..65535).
- **identity_file** — typed as `Path` parameter; not user-string input.
- **env** — already covered by `inventory_path()` against `SUPPORTED_ENVS`.

## 3. Apply points — defense-in-depth layering

```
operator-controlled string → entry-point validator → resolved-path containment → write
                  ↓                  ↓                          ↓
            add_host(alias,ip,user)                       host_vars/<alias>.yml
            write_ssh_config(alias,host,user)             config.d/<alias>.conf
            prompt_new_host()                             (reprompt on validator miss)
```

`host_vars_path()` is the single chokepoint for the inventory side — every read/write/delete goes through it, so adding `_validate_alias` + `_assert_path_in_dir` there gives transitive coverage to `read_host_vars`, `write_host_vars`, `delete_host_vars`, and `add_host` without touching each. Same chokepoint pattern applies to `write_ssh_config` for the SSH-config side.

`delete_ssh_config` preserves its `never raises` contract by swallowing `VpsRunnerError` → `return False`. Callers (CLI `_cmd_remove`) treat False as "wasn't there" — semantically equivalent to "alias was malformed so we never wrote a file by that name in the first place". No behavior regression.

## 5. NOT done (explicit)

- **Public-API alias for validators** — `_validate_alias` etc. are intentionally private. If a future caller outside `plugins.vps_runner.*` needs to validate an alias (e.g., a controller-side action), promote the names then; not now.
- **`hostname` IPv6-bracket support** — SSH config technically accepts `[2001:db8::1]:port`-style in some contexts; R9 rejects `[` and `]` neither in nor out of the policy. Real-world IPv6 aliases at this fleet use bare IPv6, which the regex accepts. If brackets ever become needed, extend the regex.
- **Schema-driven validation** — could expose policy via `jsonschema` for cross-tool reuse. Not done; pure-regex is sufficient at the current API surface.
- **No external review yet** — R9 touches no destructive sinks (W-R20 trigger). Pre-`merge-to-dev` `/ultrareview` covers the whole-branch review later, as planned in R7 §6.
