## 2. Intent per change

### 2.1 The regression itself

Legacy `plugins/vps_manager/cli.py` (deleted in Round 4-b) had three lifecycle UX subcommands the plan-2026-05-16 omitted:
- `new` — interactively create an onboard VPS task draft
- `submit` — move a validated draft task into pending
- `tasks` — list VPS Manager task files by state

Plan-2026-05-16 §1.2 scope listed only "onboard / audit / modify / remove / list" — five runtime *actions*, missing the three *lifecycle UX* commands. Round 4-b cutover removed `make vps-new` / `vps-submit` / `vps-tasks` / `vps-recover` without porting equivalents.

Net effect on the new branch: to add a managed VPS, operators had to hand-write `inventory/vps_runner/<env>/host_vars/<alias>.yml` + manually edit `hosts.yml` BEFORE calling `onboard`. Surfaced by user trying to do exactly this in a real workflow.

### 2.2 `add-host` over `new`

Old `new` name was tied to "create a task draft" semantics — there are no task drafts anymore. `add-host` matches the verb-noun convention of sibling Ansible tools (e.g., `ansible.builtin.add_host` is the in-play module that adds to runtime in-memory inventory; our `add-host` is the on-disk equivalent). Naming overlap is intentional: Ansible-fluent operators will guess correctly.

### 2.3 Defaults matching fleet conventions

- `port=1156` — all 4 existing dev hosts use this
- `user=ansible` — matches 3 of 4 existing hosts (hy-hk-u24 uses `deploy`, overrideable via `--user`)
- `status=pending` — explicit "not yet onboarded" signal; onboard flips to `active` via existing `record_run(set_status="active")` codepath on success

### 2.4 Validation = fail-fast at CLI time

Port validation mirrors `onboard.yml` `pre_tasks` assertion exactly (`!= 22 and 1024..65535`). Same constraint, but enforced at `add-host` invocation instead of waiting until `onboard` runs and fails mid-play. Operator gets a clear error in 0.05s instead of after 5 min of onboarding.

Duplicate alias check covers both "host_vars exists" AND "alias in hosts.yml" (orphan case where one source got cleaned but the other didn't). Either condition rejects the add — operator must clean before retrying.

IP/hostname: only "non-empty" check (no regex). Ansible's `ansible_host` accepts both IPv4 and DNS names; strict format check would reject valid input. If onboard fails on bad IP, error surfaces clearly there.

### 2.5 Make wrapper namespacing (caught in iteration 1)

Initial Makefile used `PORT=` and `USER=` env-style vars. Gate 3 canary (`make vps-add-host ALIAS=test-canary-r6 IP=192.0.2.99`) revealed Make-inherited shell `USER` variable polluted `$(if $(USER),--user $(USER))`, injecting `--user netcup` (the shell's effective user) when the operator had not specified `USER` at all. This would silently override the `user=ansible` default with whoever ran `make`.

Renamed to `MANAGED_USER` / `MANAGED_PORT` — namespaced enough that no shell env collides. Cost: slightly more typing in the `make` invocation; benefit: correctness. Docs updated to call out the rename.

### 2.6 Inventory comment header update

`inventory/vps_runner/dev/hosts.yml` had a comment line "Add a node: vps-runner onboard <alias>..." that was misleading — onboard requires the host_vars file to already exist; it doesn't create the inventory entry itself. Updated to point at `add-host` first, then `onboard`, plus a heads-up about PyYAML comment loss on first run.
