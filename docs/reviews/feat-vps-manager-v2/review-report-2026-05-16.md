## 2. 技术可行性分析 (Technical Feasibility Audit)

基于 Google Web Search 与官方文档的核验结果：

### 2.1 执行引擎：ansible-runner (Standard Pattern)
- **调查验证**：`ansible-runner` 是 Red Hat/Ansible 官方为 AWX 和集成应用提供的标准 Python 接口。相比 `subprocess`，它提供了结构化的事件流（JSON events），这是实现「per-host 故障定位」的最优解。
- **方案评估**：方案 §3.3 采用 `ansible_runner.run()` 替代 `subprocess.Popen`，符合最佳实践。

### 2.2 状态管理：标准 Inventory (SSOT Principle)
- **调查验证**：对于中等规模节点（< 100），采用 `inventory/<env>/hosts.yml` 配合 `host_vars/` 目录是 Ansible 社区最推崇的组织方式。这保证了「单一事实来源」(Single Source of Truth)。
- **方案评估**：方案 §3.2 彻底废弃了 `vps_inventory.yml`，改为标准 `host_vars/`，极大提升了与原生 Ansible 工具链的互操作性。

### 2.3 并发与批处理 (Native Scaling)
- **调查验证**：Ansible 内部的 `forks` 机制足以处理数百个节点的并发。自写 Python 线程池管理子进程是典型的 **反模式**。
- **方案评估**：方案 §3.5 明确放弃了在插件层实现 batching 的补丁方案，转而利用 Ansible 原生的 `forks=20` 机制。
