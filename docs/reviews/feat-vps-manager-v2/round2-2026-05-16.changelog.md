## 2. Intent per change

### 2.1 Dependencies (T2.1)
ansible-runner added in both `requirements.txt` and `pyproject.toml`. Aligned with project [[version-policy]] (using `>=` floor, not `==` pin).

### 2.2 Inventory migration (T2.2)
**Path decision**: Used `inventory/vps_runner/<env>/` instead of `inventory/<env>/hosts.yml` (plan §3.2 default) because existing `inventory/dev/hosts.ini` already defines a different topology (legacy webservers/dbservers) and merging would conflate semantics. The dedicated `inventory/vps_runner/` subtree:
- keeps vps_runner inventory cleanly isolated from existing inventory artifacts
- doesn't touch `inventory/hosts.ini` (fleet hub/targets topology)
- lets future reality_deploy etc. cross-reference vps_runner inventory by explicit path

**host_vars schema**: connection params (ansible_host/port/user/...) + role variables (security, features) flat at top + lifecycle metadata under nested `vps_runner:` key. CLI reads/writes `vps_runner:` subtree; Ansible playbooks use top-level keys.

### 2.3 Plugin scaffold (T2.3) — adjusted from plan §4
**Plan deviation (W-R7 — surfacing immediately)**: Plan §4 T2.3 says "骨架 + playbooks/onboard.yml (复用旧 vps_manager 的 onboard playbook 逻辑)". On reading old `plugins/vps_manager/playbooks/onboard.yml`:
- 545 lines, 13 `vps_task.*` references plus deep coupling to inbox-mode variables
- Faithful migration to standard playbook requires careful per-task rewriting + retest
- T2.3 budget (1.5h) is insufficient

**Adjusted scope for round 2**: scaffold + small `audit.yml` (60 lines, ping + uptime + disk + memory) — this still demonstrates the full ansible-runner integration stack end-to-end without rewriting hundreds of lines under time pressure. Onboard playbook rewrite moved to **round 3 T3.1**.

### 2.4 CLI subcommands (T2.4) — adjusted from plan §4
**Plan deviation**: Plan T2.4 says "onboard 子命令端到端". Round 2 instead delivers `list` + `audit` subcommands — these are sufficient to demonstrate the core ansible-runner range (sync inventory read + async playbook execution + structured per-host result extraction). `onboard / modify / remove` are stubs returning EX_USAGE with pointer to round 3.

### 2.5 ansible-runner integration applied codex r1 amendments
Per codex review r1 (fully verified via WebFetch — see review-2026-05-16-codex §1.2–1.3):
- `project_dir=PROJECT_ROOT` + playbook relative path (avoids `private_data_dir/project` default)
- `inventory=` **absolute path** (codex r1 #2 — never depend on ansible.cfg default `inventory = inventory/prod`)
- `artifact_dir=runtime/logs/vps_runner` + `ident=run_id` (predictable artifact location)
- `suppress_env_files=True` (codex r1 #3 — secrets never written to disk; spike-verified before T2.1)
- `rotate_artifacts=10` (codex r1 #3 — bounded retention window)
- `forks=20` explicit (codex r1 #1 — Ansible default is 5; ansible.cfg has no `forks` setting)
