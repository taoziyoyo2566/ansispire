- ✅ 旧 `plugins/vps_manager/` 在阶段 4 完整删除后，`make verify` 全绿；CHANGELOG 记录 cutover

## 2. Gap Analysis（旧 vs 新）

| 维度 | 旧 vps_manager (反范式) | 新 vps_runner (Ansible 范式) |
|---|---|---|
| 执行 API | `subprocess.Popen(['ansible-playbook', ...])` + `select.select(proc.stdout)` 轮询 | `ansible_runner.run(playbook=..., inventory=..., extravars=...)` |
| 调度 | inbox 文件 + per-task 串行 `process_file` | CLI 子命令直接调用 `run()`；多节点走标准 inventory group |
| Inventory | `runtime/state/vps_inventory.yml`（自定义 schema，每 task 临时生成单 host inventory） | `inventory/<env>/hosts.yml` + `host_vars/<alias>.yml`（标准 Ansible 格式，跨 run 复用） |
| 并发 | 没有（per-task subprocess 互不并发） | Ansible forks（默认 5；**显式覆盖到 20**：通过 `ansible_runner.run(forks=20)`，并在 ansible.cfg `[defaults]` 加 `forks = 20` 作为 fallback default。**修订自 codex r1 #1**——本表原写 "ansible.cfg 既有 forks=20" 是事实错误，ansible.cfg 当前无此设置）|
| 结果收集 | returncode + 自写 `redact_text` + `human_log.py` 美化 stdout | `Runner.host_events(alias)` + `Runner.stats`（per-host 结构化） |
| State 持久化 | `runtime/state/vps_inventory.yml` 维护「servers 字典」 | 标准 `inventory/<env>/host_vars/<alias>.yml`（Ansible 直接读） |
| 操作日志 | `runtime/logs/vps_manager/<task_id>.log`（自管） | `runtime/logs/vps_runner/<run_id>/artifacts/`（ansible-runner 自管，含 events.jsonl + stdout） |
| Archive | `runtime/archive/vps/{success,failure}/<task_id>/`（自写 redact） | ansible-runner artifacts + 选择性 retention（Ansible 推荐做法） |
| 安全（密码） | inbox 内 `password_env` + `prompt_for_missing_passwords` | `extravars={'ansible_password': os.environ[...]}`（同等安全） + `--ask-pass` 路径备选 |
| 跨子系统 import | `vps_manager.py` 1175 行单文件 | `vps_runner.py` 目标 < 500 行（薄壳：CLI → ansible-runner，复杂度推到 Ansible playbook） |
| schema 校验 | `plugin.yaml` + `schema.json` 自验 + ValidationError | CLI argparse 校验 + inventory 由 Ansible 自身校验 |

## 3. 设计决策（Decisions）

### 3.1 新 plugin 名（默认 `vps_runner`，见 §6 D1）

`vps_runner` 直接表达「围绕 ansible-runner 构建」，与旧 `vps_manager` 不冲突，路径独立。

### 3.2 Inventory 模型

```
inventory/
  dev/
    hosts.yml                  # 节点声明（aliases + groups）
    host_vars/
      hy-hk-u24.yml           # 节点详情（host, port, user, ssh_key, status, ...）
      hk-d13.yml
  stag/
    hosts.yml
    host_vars/
      ...
  prod/
    hosts.yml
    host_vars/
      ...
```

- **不再有** `runtime/state/vps_inventory.yml`——所有 host 状态都在 `host_vars/<alias>.yml` 里，Ansible 原生读取
- onboard 时 plugin 写 `inventory/<env>/hosts.yml` + `inventory/<env>/host_vars/<alias>.yml`；不再写 `runtime/state/`
- modify 时直接编辑对应 `host_vars/<alias>.yml`

### 3.3 Execution API（核心）

**修订自 codex r1 #2**：原草案 `private_data_dir=runtime/logs/.../{run_id}` + `playbook="plugins/vps_runner/playbooks/X.yml"` 会去 `runtime/logs/.../{run_id}/project/...` 找 playbook（因为 ansible-runner 默认相对 `private_data_dir/project` 解析），必然 FileNotFoundError。改用 `project_dir` + 绝对路径 + `artifact_dir` + `ident` 显式控制。

```python
# plugins/vps_runner/vps_runner.py（草案，示意结构）
import ansible_runner
from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parents[2]

def run_action(action: str, env: str, limit: str | None = None,
               extravars: dict | None = None, forks: int = 20):
    run_id = generate_run_id()  # e.g. "vps-runner-20260516-143052"
    runner = ansible_runner.run(
        project_dir=str(PROJECT_ROOT),
        playbook=f"plugins/vps_runner/playbooks/{action}.yml",
        inventory=str(PROJECT_ROOT / "inventory" / env),
        artifact_dir=str(PROJECT_ROOT / "runtime" / "logs" / "vps_runner"),
        ident=run_id,
        limit=limit,
        extravars=extravars or {},
        envvars={"ANSIBLE_CONFIG": str(PROJECT_ROOT / "ansible.cfg")},
        suppress_env_files=True,    # codex r1 #3 — 防 secrets 落盘
        rotate_artifacts=10,         # codex r1 #3 — 限制保留窗口
        forks=forks,                 # codex r1 #1 — 显式覆盖默认 5
    )
    # 结果走 runner.stats + runner.host_events()
    return runner
```

**关键点（codex r1 + claude self-audit 修订后）**：
- `project_dir=PROJECT_ROOT` —— playbook 路径相对项目根解析（不依赖 private_data_dir/project 约定）
- `inventory=` **绝对路径**直接指向标准目录，Ansible 自己解析 hosts.yml + host_vars/；**严禁**省略此参数依赖 ansible.cfg 的 `inventory = inventory/prod` 默认值（否则会默认对 prod 跑——危险）
- `artifact_dir` + `ident` —— artifacts 落 `runtime/logs/vps_runner/<run_id>/`，可控可清理
- `suppress_env_files=True` —— secrets 不会被写到 `private_data_dir/env/`（**主防线**）
- `rotate_artifacts=10` —— 即使有泄露也限制保留窗口
- `forks=20` —— 显式传，不依赖 ansible.cfg（同时 ansible.cfg `[defaults]` 也加 `forks = 20` 作为非 Python 路径的 fallback）
- `limit=` 支持 group/host pattern（`reality_nodes`、`alias1,alias2`、`basic:!premium` 等 Ansible 原生语法）
- `extravars=` 仅传 task-specific 数据（如 onboard 时的 new alias 信息）；敏感字段如 `ansible_password` 配合 onboard playbook 的 `no_log: true`
- **不写** callback plugin——`runner.events` / `runner.host_events(alias)` 已等价

### 3.4 CLI 入口

```
vps-runner onboard <alias> --host X --user Y --auth password|key --env dev|stag|prod
vps-runner audit [--limit GROUP_OR_ALIAS] [--env ...]
vps-runner modify <alias> [--port N] [--add-user U] [--env ...]
vps-runner remove <alias> [--env ...]
vps-runner list [--env ...]
```

- 移除 inbox 模式（pending/processing/done 全部砍掉）
- 每条命令立即同步执行（不再有「写文件 + 异步处理」）
- 多节点操作通过 `--limit` 走 Ansible 原生 group pattern

### 3.5 多节点 batch（自然落地）

- `audit / modify / remove` 通过 `--limit GROUP` 直接对多节点跑——Ansible forks（§3.3 显式传 20）自动并发
- `onboard` 仍是单节点（每节点配置独立）；但**多个 onboard 并行**通过 shell 后台或 GNU parallel 解决（plugin 不内置 batch onboard）
- 这是符合 Ansible 范式的——Ansible 本身就处理"一个 playbook 对 N 个 host"，不需要 plugin 层做合并

### 3.6 与旧 vps_manager 的关系

| 阶段 | 旧 vps_manager 状态 |
|---|---|
| 实施 round 2-3 | 完整保留（代码 + Makefile target + CI），新插件平行存在 |
| 实施 round 4 cutover | user 验证新插件 OK 后，单 commit 删除 `plugins/vps_manager/` + `docs/operations/vps-manager.md` + `docs/reference/feature-map/vps-manager.md` + Makefile target + CI 步骤 + CHANGELOG 记录 |
| Cutover 后 | 旧代码完全删除（git 历史保留作 reference） |

**不复用任何模块**（hard rule，见 W-R18 second corollary）。

### 3.7 安全与密码（修订自 codex r1 #3 + claude self-audit）

**三层防御**（事后 redact 降级为补防线，不再当主防线）：

| 层 | 机制 | 实施位置 |
|---|---|---|
| **L1 主防线** | `suppress_env_files=True` 防 secrets 写到 `private_data_dir/env/` | §3.3 `ansible_runner.run()` 调用 |
| **L2 二线** | 敏感 task 标 `no_log: true`（处理 password / vault / ssh key 的 task） | onboard.yml / modify.yml 任何接触 `ansible_password` / `ansible_ssh_pass` 的 task |
| **L3 三线** | `rotate_artifacts=10` 限制 artifact 保留窗口（即使有泄露也限制 blast radius） | §3.3 `ansible_runner.run()` 调用 |
| L4 补防线 | 后处理 redact（grep + sed 已知 pattern） | 仅作为额外保险，不作为唯一手段 |

**其他**：
- onboard 时密码：优先 `cmdline=['--ask-pass']`（交互输入，不进 disk）；批量场景才用 `extravars={'ansible_password': os.environ[ENV_NAME]}`（配合 L1+L2）
- ansible-runner artifacts 路径全部在 `runtime/logs/vps_runner/`（已 gitignored）
- `inventory` 参数（§3.3）必须显式传，**禁止依赖 ansible.cfg 的 `inventory = inventory/prod` 默认值**（dev/stag 操作默认对 prod 跑是高危）；unit test 验证此约束

## 7. 风险与回滚

- **R1 风险**：ansible-runner 在 venv 内行为可能与 EE 容器不一致（旧 vps_manager 没用 EE，新插件也不依赖 EE，但要在 round 2 实测确认）。**回滚**：发现严重不兼容时退回到 `subprocess.Popen` —— 但本 plan 整个 P&S 都基于 ansible-runner，应该提前 round 2 起前先做 30 分钟 spike
- **R2 风险**：onboard playbook 复用旧逻辑时含 inbox-mode 假设（确定有 `vps_task` / `vps_task_id` / `vps_plugin_dir` / `vps_project_root` 等变量）。**缓解**：T2.3 提取 playbook 时全量替换：变量改用 host_vars/<alias>.yml + extravars 注入；grep `vps_task` 应该归零后再 commit
- **R3 风险**：cutover 时 CI 可能依赖 vps_manager 测试（之前 IVG-DEEP-AUDIT B3 提到 CI 没跑 vps_manager 测试）——其实是 OK 的，反而简化 cutover；但要 grep `.github/workflows/` 一遍确认
- **R4 风险（claude self-audit 补）**：ansible.cfg 默认 `inventory = inventory/prod` + `become_ask_pass = False`——dev/stag 操作若忘传 inventory 会默认对 prod 跑（高危）；新节点 sudo 配置可能要求密码（hostinger 等 provider 默认不允许 NOPASSWD），第一次 onboard 必须支持 `--ask-become-pass` 路径。**缓解**：§3.7 已规定 inventory 必须显式传 + unit test 验证；onboard 子命令加 `--ask-become-pass` flag
- **R5 风险（claude self-audit 补）**：`suppress_env_files=True` 与 `envvars={ANSIBLE_CONFIG: ...}` 的交互——按文档 envvars 也会经 env file 落盘，suppress 后是否还会 inject 到子进程 env 需要实测。**缓解**：T2.1 之前先做 30 分钟 spike：跑一个 trivial `ansible_runner.run(envvars={'TEST': 'X'}, suppress_env_files=True)` + ansible task 用 `lookup('env', 'TEST')` 验证 env 是否生效

## 7.5 Future Migration Path: 标准 inventory → DB-backed dynamic inventory

> 触发：user 2026-05-16 问「节点管理最终通过数据库管理是否符合 ansible 最佳实践」。调查结论：✅ 符合（NetBox 是 Red Hat 推荐 source of truth；AWX 内部就用 PostgreSQL；自写 dynamic inventory plugin 是 Ansible 官方原生模式）。本 plan 当前阶段不做，但留接口。

### 7.5.1 当前方案为 DB 演进留的接口

本 plan 选「标准 `inventory/<env>/hosts.yml` + `host_vars/<alias>.yml`」**就是** Ansible 范式中 DB 演进的最优起点：
- Ansible inventory 是**可插拔的**——`ansible_runner.run(inventory=PATH)` 中 PATH 可以指向**静态 YAML 目录**、**动态 inventory plugin**、**inventory script**——三者对 `ansible-runner.run()` 调用者**完全透明**
- 这意味着未来切换 DB 时，`vps_runner.py` 中除了 `inventory=...` 参数路径，**其他代码零改动**

### 7.5.2 演进路径（仅供 reference，不在本 plan 实施范围）

| 阶段 | inventory source | 触发条件 | 改动量 |
|---|---|---|---|
| 现在（本 plan） | `inventory/<env>/hosts.yml` + `host_vars/<alias>.yml`（YAML 文件，git 追踪） | dev 阶段，节点数 < 50 | — |
| 中期 | 自写 dynamic inventory plugin 读 SQLite/PostgreSQL（参考 [`pginv`](https://github.com/livestalker/pginv)） | 节点数 > 50 或需要多 operator 并发写 | 新 plugin 文件 + 替换 `inventory=` 参数路径 |
| 长期 | NetBox 作为 source of truth + 官方 [NetBox Ansible inventory plugin](https://netboxlabs.com/docs/integrations/tool-integrations/netbox-ansible-collection/) | 需要 IPAM / DCIM 集成 / cross-team CMDB | 部署 NetBox 服务 + 配置 inventory plugin + 数据迁移 |

### 7.5.3 演进决策原则

- **基础设施数据归 inventory plugin**：host、port、ssh key、status、group 关系——走 NetBox 或自建 CMDB
- **业务数据不要塞 inventory**：业务用户、订阅、ACL 业务规则——归应用层 DB（与 reality_manager Future Migration 协同，见 reality-migration plan §7.5）
- **Secrets 演进**：production 上 DB 后，private_key / passwords 应改走 HashiCorp Vault（动态 secrets + rotation），不要塞 PG 明文字段
- **dynamic inventory 必启用 `cache: true`**（production 标配），避免每次 playbook 跑都打 DB

### 7.5.4 为什么现在不做

- **W-R14 / [[dev-stage-pragmatism]]**：dev 阶段引入 NetBox 是过度工程
- 节点数 < 50 + 单 operator → YAML 完全够
- 抽象接口已经在了（standard inventory 路径）——未来切换改动量本来就小，不需要"提前优化"
